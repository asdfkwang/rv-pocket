# 챕터 21 — TLB와 페이지 폴트

> **Part V — Memory Becomes Virtual**

## 왜 변환이 없다는 것이 항상 fault는 아닌가?

챕터 20은 최종 데이터 접근 전에 세 번의 페이지 테이블 읽기를 요구했습니다. TLB(Translation Lookaside Buffer)는 최근에 쓴 변환과 관련 권한을 캐시합니다. 데이터 캐시와 다릅니다: 그 답은 페이로드가 아니라 주소가 어디에 어떤 권한으로 접근될 수 있는지입니다.

TLB 미스는 필요한 변환이 그 캐시에 현재 없다는 뜻입니다. 페이지 폴트는 변환이나 접근 검사가 요청된 연산을 승인하지 못했다는 뜻입니다. 미스는 성공적인 하드웨어 walk를 유발할 수 있으며 OS 개입을 전혀 요구하지 않을 수도 있습니다.

## 하나의 가상 주소에 대한 세 경로 비교

챕터 20의 가상 페이지 `0x40403000`에서 물리 페이지 `0x82005000`으로의 매핑을 사용합니다.

| 상황 | 변환 동작 | 결과 |
| --- | --- | --- |
| 유효한 일치 TLB 항목 | 캐시된 페이지와 권한 사용 | 물리 오프셋 위치에 접근 |
| TLB 항목 없음, 유효한 페이지 테이블 | 테이블을 walk하고 결과는 적절히 캐시 | 동일한 허용된 접근 |
| 사용 가능한 변환 없음, 리프 무효 | walk가 접근을 승인할 수 없음 | OS로 페이지 폴트 |

두 번째 행에서 추가 작업은 주로 하드웨어 변환 작업입니다. 세 번째 행에서 OS는 fault를 프로세스의 의도된 매핑에 비추어 해석해야 합니다. 리프가 없다는 것은 유효한 demand 할당 페이지가 아직 채워지지 않았다는 뜻일 수 있고, 프로그램이 잘못된 포인터를 썼다는 뜻일 수도 있습니다. PTE만으로 커널의 메모리 관리 정책 전체가 정해지지 않습니다.

복구 가능한 익명 메모리 fault의 경우 커널은 물리 페이지를 할당하고 초기화하고, 적절한 동기화와 함께 매핑을 설치하고, 명령어를 재시도할 수 있습니다. 챕터 13에서 왜 저장된 PC가 fault가 난 load나 store에 머무는지 설명했습니다. 할당이 실패하거나 주소가 허용되지 않으면 응답이 달라집니다.

## copy-on-write fault는 의도적일 수 있다

copy-on-write 정책으로 프로세스 사이에 페이지를 공유한 뒤 OS는 두 매핑을 모두 읽기 전용으로 표시할 수 있습니다. 읽기는 원래 페이지를 공유합니다. 쓰기는 fault를 일으켜 커널이 기록자를 위한 사사본을 할당하고 매핑을 바꾼 뒤 store를 재시도하게 합니다.

```text
쓰기 전: A의 VA -> 공유 페이지 P, 읽기 전용
          B의 VA -> 공유 페이지 P, 읽기 전용
A가 씀:   보호 fault
커널:     P를 Q로 복사; A의 VA -> Q로 매핑, 쓰기 가능
재시도:   A의 store가 Q를 변경; B는 P를 계속 읽음
```

여기의 페이지 폴트는 정책이 깨진 프로그램을 보고하는 것이 아니라 정책을 구현합니다. 저장장치 I/O를 필요로 하지 않을 수도 있습니다. 다른 fault는 파일이나 스왑에서 데이터를 가져와야 하고, 많은 것은 전부 메모리 안에서 해결됩니다.

## 테이블을 갱신하는 것이 모든 캐시된 답을 갱신하는 것은 아니다

CPU가 `VA -> P`를 캐시했고 OS가 PTE를 `VA -> Q`로 바꿨다고 합시다. 일관적인 데이터 캐시 시스템은 새 PTE 바이트를 보이게 할 수 있지만 CPU는 여전히 오래된 변환을 갖고 있을 수 있습니다. 데이터 일관성은 캐시된 주소 변환 상태를 자동으로 대체하지 않습니다.

RISC-V의 SFENCE.VMA는 관련 로컬 주소 변환 상태에 필요한 순서화/무효화 연산을 제공합니다. 피연산자는 아키텍처 규칙 아래에서 주소와 주소 공간 범위를 제한할 수 있습니다. CPU 캐시에서 페이로드 데이터를 flush하는 범용 명령이 아닙니다.

다른 CPU가 그 매핑을 사용할 수 있다면, OS는 오래된 변환이 아직 도달할 수 있는 메모리를 재사용하기 전에 조정된 원격 연산(보통 TLB shootdown이라 부릅니다)이 필요합니다. 시작한 CPU는 자신의 fence를 실행하는 것만으로 다른 CPU의 로컬 변환 의무를 만족시킬 수 없습니다.

안전한 개념적 순서는 이렇습니다: 커널의 페이지 테이블 규칙에 따라 매핑 변화를 공개하고, 필요한 로컬과 원격 변환 동기화를 준비하고, 필요한 완료를 기다린 뒤, 유효한 참조가 남아 있지 않을 때만 옛 페이지를 재사용합니다. 너무 일찍 재사용하면 오래된 변환이 무관한 객체의 데이터에 접근하는 것으로 바뀔 수 있습니다.

챕터 22는 또 다른 메모리 행위자로 장치를 더합니다. 장치의 주소 관점은 애플리케이션의 관점이나 CPU의 물리 관점과 다를 수 있습니다.

## 체크

1. TLB 미스가 하드웨어 walk 중 유효한 허용 매핑을 찾습니다. 그 뒤에는?
   - A) 프로세스를 죽여야 합니다.
   - B) 페이지 fault 핸들러 없이도 접근이 진행될 수 있습니다.
   - C) 페이지를 디스크에서 읽어야 합니다.
   - Answer: B
   - Explanation: 캐시된 변환이 없다는 것과 매핑이 유효하지 않다는 것은 서로 다른 상황입니다.

2. OS 처리를 요구할 수 있는 것은? 모두 고르세요.
   - A) 의도적인 copy-on-write 쓰기 fault
   - B) 허용되지 않은 user 주소 접근
   - C) 성공한 모든 하드웨어 TLB 리필
   - Answer: A, B
   - Explanation: fault 정책은 소프트웨어가 처리합니다. 성공한 하드웨어 walk는 trap이 필요 없습니다.

3. copy-on-write 추적에서 A가 바이트 오프셋 8을 변경하기 전후의 페이지 내용을 보이세요. B가 무엇을 관찰하는지, 의도한 공유 정책을 위반하지 않고 Q가 언제 쓰기 가능해질 수 있는지 식별하세요.

4. 원격 TLB 동기화가 끝나기 전에 P를 해제해서 발생하는 2CPU use-after-reassignment 버그를 구성하세요. 평범한 데이터 캐시 일관성이 왜 그것을 막지 못하는지 설명하세요.

5. Research challenge: SFENCE.VMA와 satp 갱신 주변 규칙을 살펴보세요. satp 쓰기가 필요한 변환 동기화의 보편적 대체책이 아닌 이유를 설명하고, 주소 공간 식별자의 역할을 기술하세요.

## 정확성의 경계

fault와 shootdown 순서는 개념적입니다. 리눅스는 아키텍처별 페이지 테이블 잠금, 참조 추적, TLB API를 제공합니다. 드라이버 작성자가 이것을 임의의 CSR 연산으로 대체해서는 안 됩니다. 페이지 크기, ASID, accessed/dirty 비트 메커니즘은 예제를 넘는 경우를 더합니다.
