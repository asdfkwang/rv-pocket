# 챕터 26 — 디바이스 트리: 컴퓨터를 기술하는 방법

> **Part VI — How Linux Finds Hardware**

## 리눅스는 하드웨어가 어디 있는지 어떻게 배우는가?

커널은 무언가 응답하기 전까지 임의의 주소를 읽어 단순한 메모리 맵 주변장치를 일반적으로 발견할 수 없습니다. 일부 버스는 열거를 지원하지만, 많은 온칩 장치는 펌웨어가 제공한 설명이 필요합니다. 디바이스 트리는 하드웨어 노드, 자원, 관계를 기술해 소프트웨어가 적절한 장치 객체를 만들 수 있게 합니다.

설명은 모든 장치를 초기화하는 코드가 아니라 데이터입니다. 올바른 노드가 클록을 켜거나 리셋을 풀거나 드라이버의 존재를 보장하지는 않습니다. 커널과 드라이버가 문서화된 바인딩을 통해 해석하는 정보를 제공합니다.

## 허구의 노드 하나 완전히 해독하기

이 예시 트리는 교육용 UART를 기술합니다. 그 발명된 호환 문자열은 일치하는 교육용 드라이버와 바인딩을 요구합니다. 기존 리눅스 UART 바인딩이 아닙니다.

```dts
/ {
    #address-cells = <2>;
    #size-cells = <2>;
    soc {
        compatible = "simple-bus";
        #address-cells = <2>;
        #size-cells = <2>;
        ranges;
        uart@10000000 {
            compatible = "rvpocket,teaching-uart";
            reg = <0x0 0x10000000 0x0 0x1000>;
            status = "okay";
        };
    };
};
```

부모의 주소/크기 cell 개수가 reg를 어떻게 나눌지 결정합니다. 각 cell은 32비트입니다. 첫 두 cell이 주소 `0x0000000010000000`를 이루고 다음 두 cell이 크기 `0x0000000000001000`를 이룹니다. 반열린 구간은 `[0x10000000, 0x10001000)`입니다. 마지막 포함 바이트는 `0x10000FFF`로 챕터 09와 일치합니다.

빈 ranges 속성은 이 버스와 부모 사이의 항등 변환을 선언합니다. 다른 버스에서는 ranges가 자식 주소를 다른 부모 주소로 변환할 수 있습니다. 따라서 자식의 reg 값은 부모 변환 전에는 CPU 물리 주소일 필요가 없습니다. ranges 생략이 명시적 항등 변환 선언과 항상 동등한 것은 아닙니다.

`@` 뒤의 단위 주소는 트리 규약에서 노드의 주소를 식별합니다. reg를 대체하지 않습니다. 호환 문자열은 소프트웨어가 매칭할 수 있는 프로그래밍 모델을 식별합니다. 사람이 읽을 수 있는 제품 이름에 그치지 않습니다.

## 노드에서 probe 시도로

적절히 채워진 버스에서 리눅스는 변환된 자원을 가진 장치 표현을 만듭니다. 버스의 매칭 규칙이 이를 등록된 드라이버와 비교합니다. 일치하면 probe 시도가 허용되며, 드라이버가 자원을 획득하고 상태를 초기화합니다. 매칭은 성공한 초기화와 같지 않습니다.

```text
펌웨어 설명
    → 버스/장치 생성
    → 사용 가능한 드라이버와 호환 일치
    → probe가 자원 받음
    → 초기화 성공 또는 실패/defer 조건 보고
```

교육용 조각은 인터럽트, 클럭, 리셋, 핀을 생략합니다. 이들의 제공자 바인딩이 먼저 명시되어야 그 cell을 해석할 수 있기 때문입니다. 임의의 `interrupts = <5>`를 추가해도 자기 설명적으로 되지 않습니다: 인터럽트 부모의 #interrupt-cells와 바인딩이 cell의 의미를 결정합니다. 챕터 28에서 probe 동안 획득되는 자원과 의존성을 다룹니다.

## 기술되었지만 비활성인 장치 진단하기

노드가 존재하고 활성화됐지만 장치가 쓸 수 없다고 합시다. 관련 버스가 그것을 생성했는지, 적절한 드라이버가 존재하고 매칭됐는지, probe가 성공적으로 실행됐는지 확인하세요. probe가 클록 제공자 준비되지 않아 defer됐다면 MMIO 주소를 바꾸는 것은 도움이 되지 않습니다.

반대로 성공한 probe는 모든 설명이 올바르다는 것을 증명하지 않습니다. 잘못된 레지스터 크기나 인터럽트 경로는 누락된 영역에 접근하거나 완료를 기다릴 때까지 잠복할 수 있습니다. 바인딩의 구조와 보드의 실제 배선을 모두 검증하세요.

스키마는 많은 잘못된 속성을 잡아내지만 물리적 와이어가 선언된 핀으로 가거나 보드 설계자가 기대한 클럭을 썼다는 것을 증명할 수 없습니다. 설명은 플랫폼 증거와 대조해 볼 주장으로 다루세요.

다음 장은 일치한 드라이버를 하나의 main 함수를 가진 프로그램이 아니라 콜백과 수명의 집합으로 따라갑니다.

## 체크

1. 예시 자원 범위의 마지막 바이트는?
   - A) `0x10001000`
   - B) `0x10000FFF`
   - C) `0x10000004`
   - Answer: B
   - Explanation: 크기는 0x1000바이트이고 반열린 끝은 최종 바이트보다 하나 뒤입니다.

2. 옳은 진술은? 모두 고르세요.
   - A) 부모는 자식 주소와 크기를 인코딩하는 cell 개수를 정의합니다.
   - B) 호환 매칭은 하드웨어가 초기화를 끝냈다는 것을 증명합니다.
   - C) 버스는 ranges를 통해 자식 주소를 변환할 수 있습니다.
   - Answer: A, C
   - Explanation: 자원 해독과 드라이버 초기화는 별개의 단계입니다.

3. 부모를 address cell 1개와 size cell 1개로 바꿉니다. 같은 범위에 reg를 다시 쓰고, 원래의 네 cell을 유지하면 그 해석이 어떻게 달라지는지 설명하세요.

4. 살아 있는 트리에 노드가 있지만 동작하는 장치가 없는 경우를 조사하세요. 첫 번째 그럴듯한 원인이 증명되었다고 가정하지 않고 생성, 매칭, probe, 의존성, 자원 증거를 포함하세요.

5. Research challenge: 실제 UART 바인딩 스키마 하나를 고르세요. 제공자 바인딩을 사용해 인터럽트, 클럭, 리셋 속성을 해독하세요. 그 필수 레지스터 레이아웃을 허구 맵과 비교하고, UART라는 단어를 공유하는 것만으로 호환되지 않는 이유를 설명하세요.

## 정확성의 경계

이 DTS는 허구 하드웨어를 위한 설명용 조각이며 완전한 배포 가능한 보드 설명이 아닙니다. 리눅스는 ACPI와 열거 가능한 버스를 포함한 다른 메커니즘으로도 하드웨어를 발견합니다. 바인딩 스키마와 제공자 관계가 실제 속성의 의미를 결정합니다.
