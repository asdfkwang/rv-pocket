# 챕터 35 — 버튼 한 번, 끝에서 끝까지

> **Part VIII — A Complete System**

## 전압 변화는 어떻게 애플리케이션 이벤트가 되는가?

이제 인터럽트, 드라이버 상태, 대기 큐, 사용자 공간 인터페이스를 한 경로로 연결할 수 있습니다. GPIO 입력에 연결된 active-low 버튼을 사용합니다: 풀업이 놓인 핀을 높게 유지하고, 누르면 낮게 연결됩니다. 보드 설명이 핀, 극성, 인터럽트 관계, 입력 키 코드를 식별합니다.

GPIO 컨트롤러 드라이버는 컨트롤러와 그 인터럽트 배관을 관리합니다. gpio-keys 같은 버튼 드라이버는 버튼을 해석하고 input 서브시스템을 통해 보고합니다. 이들은 서로 다른 역할입니다. GPIO 인터럽트는 소비자(CONSUMER)와 서브시스템 로직 없이는 자동으로 키보드 이벤트가 되지 않습니다.

## raw 상태와 논리 상태를 따로 추적하기

active-low 디스크립터에 대해 raw 전기적 0은 논리적 asserted, 즉 눌림에 대응합니다. 디스크립터 기반 GPIO 접근자는 극성을 반영할 수 있습니다. 따라서 논리값을 얻은 뒤 추가 수동 반전을 적용하는 것은 의미를 두 번 뒤집습니다.

안정적인 누름, 정상 작동하는 인터럽트 경로, 선택한 검증 구간 뒤에 상태를 수용하는 디바운스 정책을 가정합니다. 디바운스는 기계적 접촉 전이가 여러 번의 의도된 누름으로 해석되는 것을 막습니다. 그 하드웨어 또는 소프트웨어 구현은 장치별입니다.

| 경계 | 상태 / 관측 |
| --- | --- |
| 놓인 상태 | raw GPIO 높음, 논리 pressed = 0 |
| 물리적 누름 | raw GPIO가 낮아짐, 접촉 전이 가능 |
| 인터럽트 서비스 | 컨트롤러/IRQ 프레임워크가 관련 소비자 경로를 분배 |
| 디바운스 수용 | 안정적 논리 pressed = 1 |
| 버튼 드라이버 보고 | `EV_KEY`, 선택된 키 코드, 값 1 |
| Input report 경계 | `EV_SYN`, `SYN_REPORT`, 값 0 |
| 애플리케이션 읽기 | 자신의 이벤트 스트림에서 이진 입력 이벤트 레코드를 소비 |
| 애플리케이션 동작 | 자신의 상태와 포커스에 따라 키를 해석 |

SYN_REPORT는 관련 입력을 업데이트를 묶습니다. 또 하나의 물리적 버튼 누름이 아닙니다. 안정적인 해제는 대응하는 키 값 0과 report 경계를 만듭니다. 사용되는 경우 반복 동작은 인터럽트 횟수에서 추론되는 것이 아니라 자체 이벤트 의미를 가집니다.

## 기다리는 애플리케이션 따라가기

애플리케이션이 `/dev/input/eventN` 스트림을 읽으며 블로킹했다고 합시다. 입력 경로가 이벤트를 큐잉하면 관련 대기자들이 실행 가능해질 수 있습니다. 스케줄러는 애플리케이션이 읽고 처리하기 전에 여전히 그것을 선택해야 합니다. 이것은 완전한 장치 경로에서 나타난 챕터 17의 웨이크업 대 실행 구분입니다.

읽히는 데이터는 구조화된 이벤트 레코드이지 문자열 "pressed"가 아닙니다. 애플리케이션은 인터페이스를 사용해 레코드 레이아웃과 읽기 결과를 처리해야 합니다. 창이 포커스를 갖지 않거나 현재 모드가 그 키에 동작을 배정하지 않았다는 이유로 의도적으로 무시할 수 있습니다. 보이는 반응은 성공적인 장치 서비스의 하류에 있습니다.

정확한 리눅스 gpio-keys 경로는 GPIO 컨트롤러와 디바운스 구현에 따라 스레드 IRQ, 타이머, 지연된 작업을 쓸 수 있습니다. GPIO 읽기가 잘 수 있는 컨트롤러를 임의의 하드드 IRQ 컨텍스트에서 단순 비수면 MMIO 읽기처럼 다룰 수는 없습니다. 프레임워크 API가 그 제약을 드러냅니다.

## 경계 증거로 누락된 누름 찾기

누름이 어떤 애플리케이션 동작도 만들지 않는다고 합시다. 먼저 적절한 관측으로 raw 핀 전이를 확립하세요. 다음으로 관련 IRQ/드라이버 경로와 수용된 논리 상태를 확인하세요. 그다음 입력 이벤트 스트림을 검사하세요. 마지막으로 애플리케이션의 소비와 해석을 검사하세요.

이벤트 리더에게 EV_KEY 누름과 SYN_REPORT가 보인다면, GPIO 드라이버 교체는 타당한 첫 결론이 아닙니다. 전기에서 input까지의 경로가 예상 레코드를 만들었습니다. 남은 실패는 접근, 이벤트 선택, 스케줄링, 애플리케이션 정책일 수 있습니다. 인터럽트는 발생하는데 키 이벤트가 보고되지 않는다면 극성, 디바운스, 소비자 라우팅, 드라이버 로직을 조사하세요.

설정된 디바운스 구간보다 짧은 펄스는 의도적으로 거부될 수 있습니다. 그런 관찰은 그것이 수용된 뒤의 안정적인 누름을 잃는 것과 다릅니다. 결과를 버그라고 부르기 전에 테스트 자극과 정책을 정의하세요.

챕터 36은 출력에 같은 경계 방법을 사용합니다. 여기서 장치는 일회성 입력 레코드를 전달하는 대신 프레임을 반복해서 읽습니다.

## 체크

1. active-low 버튼이 물리적으로 눌렸고 그 raw 핀이 낮습니다. 극성을 인식하는 디스크립터 읽기는 보통 어떤 논리값을 나타냅니까?
   - A) 눌림/asserted, 값 1
   - B) 해제. raw 전압이 0이니까
   - C) ASCII 0을 담은 문자 바이트
   - Answer: A
   - Explanation: 논리 극성은 활성 전기 레벨을 asserted 상태에 대응시킵니다.

2. 어떤 것이 서로 다른 경계입니까? 모두 고르세요.
   - A) 핀 전이
   - B) input 서브시스템이 큐잉한 이벤트
   - C) 애플리케이션이 선택한 반응
   - Answer: A, B, C
   - Explanation: 각 경계는 이후 경계가 지연되거나 필터링되거나 잘못 구성되기 전에도 성공할 수 있습니다.

3. 수용된 누름과 해제 하나에 대한 이벤트 레코드를 report 경계 포함으로 그리세요. 인터럽트 호출 횟수를 세는 것이 수용된 누름 수와 다른 결과를 줄 수 있는 이유를 설명하세요.

4. 이벤트 리더가 예상한 누름과 해제를 보지만 게임이 아무것도 하지 않습니다. 다음 진단 단계를 설계하고, 그 관찰이 어떤 이전 하드웨어 가설을 약화시키면서도 시스템 전체가 올바르다고 주장하지는 않는지 밝히세요.

5. Research challenge: 기록된 커널 리비전에서 gpio-keys를 살펴보세요. 설정된 극성과 디바운스 경로가 input 보고까지 어떻게 이어지는지 따라가고, 잘 수 있을 수 있는 GPIO 접근자를 코드가 어떻게 처리하는지 설명하세요.

## 정확성의 경계

이 경로는 리눅스 input 서브시스템으로 노출된 GPIO 기반 버튼을 가정합니다. 배선, 트리거 유형, 디바운스 정책, 커널 구성에 따라 구체적인 콜백이 달라집니다. 애플리케이션 권한, 포커스, 이벤트 정책은 물리적 인터럽트 전달을 넘어선 하류 관심사입니다.
