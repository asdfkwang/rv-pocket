# 챕터 27 — 리눅스 디바이스 드라이버란 무엇인가

> **Part VII — Linux Device Drivers**

## 드라이버는 어디서 시작하고 어디서 끝나는가?

챕터 26에서 장치 객체와 가능한 드라이버 매칭이 만들어졌습니다. 리눅스 드라이버는 등록된 연산을 통해 커널 프레임워크에 참여하는 코드입니다. 보통 main 루프를 소유하지 않습니다. 장치가 바인딩되고, 연산이 요청되고, 이벤트가 도착하고, 전원 상태가 바뀌고, 장치가 제거될 때 커널이 이를 호출합니다.

식별해야 할 두 가지 인터페이스가 있습니다. 버스 측 인터페이스는 플랫폼 드라이버의 probe와 remove 콜백 같은 매칭과 생명 주기를 처리합니다. 서브시스템 측 인터페이스는 serial, input, network, storage 같은 장치 클래스에 맞는 동작을 구현합니다. 모든 드라이버가 사용자 공간 read/write 파일 연산을 직접 구현하는 것은 아닙니다.

## 직렬 드라이버의 두 등록 따라가기

리눅스 serial 프레임워크에 맞춘 교육용 UART를 생각해 봅시다. 플랫폼 매칭이 probe로 이어집니다. probe는 장치별 상태를 준비하고 직렬 포트를 serial 서브시스템에 등록합니다. 그러면 serial 연산이 전송이나 설정 변경이 필요할 때 UART 특화 콜백을 호출합니다.

```text
플랫폼 버스                         serial 서브시스템
장치를 드라이버와 매칭               애플리케이션/TTY 요청
        |                                     |
      probe -> 포트 준비 -> 포트 등록           |
                                      -> UART 연산 콜백
                                            -> MMIO / 큐잉된 데이터
```

개념적 연산 테이블에는 start_tx, stop_rx, set_termios가 포함될 수 있습니다. 이 콜백 이름은 serial 프레임워크 계약에 속하며 임의의 read/write 메서드와 바꿔 쓸 수 없습니다. 프레임워크는 공유 정책과 배관을 처리하고 드라이버는 하드웨어 특화 부분을 구현합니다.

이 구분이 문자 장치 튜토리얼을 직렬 드라이버에 복사하면 핵심 동작을 놓칠 수 있는 이유입니다. 이미 장치의 기능을 표현하는 서브시스템에서 시작하세요. 평범한 키보드는 input 서브시스템에, 평범한 네트워크 인터페이스는 networking에 속합니다. 챕터 33에서 사용자 공간 인터페이스를 비교하며 하나의 `/dev` 설계가 모두에 맞지는 않는다고 봅니다.

## 하나의 드라이버가 여러 인스턴스를 관리할 수 있다

보드에 UART0과 UART1이 있다고 합시다. 드라이버 코드는 공유되지만 각 인스턴스는 자체 매핑된 레지스터, 인터럽트 식별자, 락, 큐, 생명주기 상태가 필요합니다. 이들을 두 번째 probe가 덮어쓰는 하나의 전역 기준 포인터가 아니라 장치별 객체에 저장하세요.

```text
공유 드라이버 코드
    장치 상태 A: 기준 A, IRQ A, 큐 A, 락 A
    장치 상태 B: 기준 B, IRQ B, 큐 B, 락 B
```

장치별 상태는 인스턴스 연관을 해결합니다. 동시에 접근하는 문제를 자동으로 해결하지는 않습니다: 같은 장치의 두 콜백이 여전히 겹치거나 다른 컨텍스트에서 실행될 수 있습니다. 챕터 18의 동기화 규칙이 객체 내부에 적용됩니다.

모든 콜백에 유용한 점검 질문은 이렇습니다: 어떻게 올바른 인스턴스를 찾는가, 어떤 컨텍스트에서 실행되는가, 어떤 자원이 살아 있다고 보장되는가? 이 세 답이 함수의 이름보다 많은 것을 설명해 주는 경우가 많습니다.

## unregistration은 설계의 일부입니다

장치를 제거할 때 공개된 인터페이스를 통해 새 연산을 멈추고, 새 장치 작업을 막고, 진행 중인 하드웨어 활동을 정지시키고, 그들이 접근하는 자원을 해제하기 전에 관련 콜백을 비우거나 동기화해야 합니다. 정확한 순서는 서브시스템과 하드웨어 프로토콜을 따릅니다. 장치별 구조체를 단순히 해제하는 것으로 대체할 수 없습니다.

해제된 객체를 사용하는 늦은 인터럽트는 MMIO 코드가 정확해도 수명 실패입니다. 매핑 해제된 기준을 쓰는 큐잉된 워커도 마찬가지입니다. 자원 관리 도구는 획득과 해제를 짝지을 수 있지만 장치의 정지 순서를 추론하거나 모든 비동기 연산을 취소해주지는 않습니다.

마찬가지로 모듈을 로드하는 것은 드라이버 코드를 사용할 수 있게 하고 등록할 뿐입니다. 장치가 매칭됐거나 probe가 성공했거나 사용자 공간 인터페이스가 사용 가능해졌다는 것을 증명하지 않습니다. 이들은 서로 다른 이정표로 진단하세요.

챕터 28은 첫 콜백인 probe를 다루고 명시적 자원 소유권을 갖는 부분 실패를 따라갑니다.

## 체크

1. 드라이버 모듈이 성공적으로 로드되었습니다. 그 사실만으로 정당화되는 결론은?
   - A) 매칭되는 모든 장치가 초기화되어 동작한다.
   - B) 모듈의 초기화가 성공했다. 바인딩과 장치 동작에는 별도 증거가 필요하다.
   - C) 장치 파일이 반드시 존재한다.
   - Answer: B
   - Explanation: 드라이버 가용성, 매칭, probe, 서브시스템 공개, 연산은 서로 다른 단계입니다.

2. 보통 장치 인스턴스에 속해야 하는 상태는? 모두 고르세요.
   - A) MMIO 매핑
   - B) 큐와 락
   - C) 모든 probe가 덮어쓰는 하나의 전역 기준 포인터
   - Answer: A, B
   - Explanation: 공유 코드가 여러 독립 인스턴스를 제공할 수 있지만, 하나의 변경 가능한 기준 포인터는 그 연관을 잃습니다.

3. UART와 입력 버튼에 대해 버스 측 경로와 서브시스템 측 경로를 그리세요. 각 프레임워크가 장치 특화 코드에 일을 넘기는 콜백 경계를 식별하세요.

4. remove 콜백이 이미 큐잉된 워커가 여전히 실행 가능할 때 장치별 객체를 해제합니다. 실패 타임라인을 구성하고 해제가 안전해지기 전에 필요한 수명 증거를 밝히세요.

5. Research challenge: 업스트림 드라이버 하나를 선택하고 커밋 하나를 기록하세요. 버스 등록, 서브시스템 등록, 장치별 상태, 비동기 콜백 하나를 식별하세요. 그 콜백이 어떻게 인스턴스를 얻고 무엇이 상태를 살아 있게 하는지 설명하세요.

## 정확성의 경계

이 장은 생명주기 수준에서 드라이버 모델을 기술합니다. 콜백 집합과 컨텍스트는 서브시스템, 버스, 구성, 커널 버전에 따라 다릅니다. 모든 드라이버가 사용자 공간 read/write 연산을 직접 필요로 한다는 템플릿이 아닙니다.
