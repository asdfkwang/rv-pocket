# 챕터 09 — 장치가 주소가 되는 방법

> **Part III — CPU Meets Hardware**

## 왜 store가 하드웨어에 동작을 일으킬 수 있는가?

지금까지 store는 RAM을 바꿨습니다. 같은 종류의 CPU 요청이 장치에 도달할 수도 있습니다. 메모리 맵 I/O, 즉 MMIO는 주소 공간의 일부를 하드웨어 인터페이스에 할당합니다. 주소 디코더는 요청의 주소로 응답 대상을 선택하고, 그 대상이 연산의 의미를 결정합니다.

여기서 레지스터는 장치의 이름 붙은 인터페이스 위치이지 CPU 레지스터 x0–x31이 아닙니다. 어떤 장치 레지스터는 구성을 유지하고, 다른 것은 실시간 상태를 드러내며, 또 다른 것은 명령이나 큐처럼 동작합니다. 주소 하나만으로는 어떤 동작이 적용되는지 알 수 없습니다.

## 교육용 플랫폼 정의하기

이 책의 이 Part에서는 다음 물리 범위에 접근할 권한이 있는 베어메탈 소프트웨어를 가정합니다. 베어메탈은 우리 코드와 하드웨어 사이에 운영체제 서비스가 없다는 뜻입니다. UART 맵은 허구이며 실제 UART 표준과 의도적으로 다릅니다.

| 물리 범위, 양 끝 포함 | 대상 |
| --- | --- |
| `0x10000000`–`0x10000FFF` | 교육용 UART |
| `0x80000000`–`0x8000FFFF` | 이 예제에 쓰는 RAM |

UART는 정렬된 32비트 리틀 엔디안 레지스터 접근을 사용합니다:

| 오프셋 | 이름 | 초기 규약 |
| --- | --- | --- |
| `0x00` | TX_DATA | 준비되면 하위 8비트를 송신기에 씁니다 |
| `0x04` | STATUS | 읽기: 비트 0 TX 준비; 비트 1 RX 데이터 있음 |
| `0x08` | RX_DATA | 있으면 수신 바이트 하나를 읽고 소비합니다 |
| `0x0C` | IRQ_ENABLE | 비트 0이 수신 이벤트 알림을 활성화 |
| `0x10` | IRQ_STATUS | 래치된 이벤트; 선택한 비트를 지우려면 1을 씁니다 |
| `0x14` | CONTROL | 읽기/쓰기 구성, 비트 0이 장치를 활성화 |

뒤의 장들이 이벤트 프로토콜을 명시한 뒤 사용합니다. 이 표는 주소와 기본 접근 의미를 주며, 프로덕션 UART 구현이 아닙니다.

## 디코더를 통과하는 store 따라가기

x10이 `0x10000000`, x12가 `0x41`를 담고 있고, CONTROL이 UART를 활성화하며 STATUS 비트 0이 설정됐다고 합시다. `sw x12, 0(x10)`을 실행합니다.

CPU는 주소 `0x10000000`을 만들고 `0x00000041`을 담은 4바이트 쓰기를 발행합니다. 인터커넥트가 이를 UART 범위로 라우팅합니다. UART는 오프셋 0을 디코딩해 하위 바이트를 송신 경로에 넣습니다. 다른 바이트를 받을 수 있을 때까지 TX 준비 비트를 지울 수 있습니다. 그 주소의 RAM 위치는 갱신되지 않았습니다. 그 물리 주소는 다른 대상을 선택하기 때문입니다.

이제 x10을 `0x80000000`으로 바꾸고 같은 명령어를 실행합니다. 선택된 대상은 RAM이며 바이트 `41 00 00 00`이 저장됩니다. 같은 명령어와 데이터, 다른 주소, 다른 효과입니다. ISA는 요청을 정의하고, 플랫폼 맵과 장치 명세가 대상의 반응을 정의합니다.

이것이 readback이 보편적으로 쓰기의 검증이 아닌 이유이기도 합니다. 명령 레지스터 읽기는 지원되지 않을 수 있고, 무관한 상태를 돌려줄 수 있으며, 부작용이 있을 수 있습니다. 요청한 연산을 관측해야 한다면 문서화된 상태 레지스터를 읽으세요.

## 매핑은 포인터 캐스팅만이 아니다

베어메탈 추적은 물리 주소를 직접 씁니다. 가상 메모리가 있는 OS 아래에서는 CPU 명령어가 쓰는 주소가 먼저 변환될 수 있습니다. 수치적인 물리 장치 주소가 자동으로 유효한 커널 포인터가 되지는 않습니다. 리눅스 드라이버는 자원을 얻어 적절한 커널 I/O 매핑으로 매핑한 뒤 `readl`과 `writel` 같은 MMIO 접근자를 씁니다. 챕터 29에서 그 경로를 구체적으로 따라갑니다.

매핑의 메모리 속성도 중요합니다. 평범한 RAM은 캐시되거나 투기적으로 접근될 수 있습니다. 장치 읽기는 데이터를 소비할 수 있습니다. 장치 영역을 평범한 캐시 가능 메모리처럼 다루면 장치가 관찰하는 연산의 횟수와 타이밍이 바뀔 수 있습니다. C의 `volatile`만으로 플랫폼 매핑이 확립되거나 커널의 I/O 규약이 제공되지는 않습니다.

## 주소 오류와 장치 상태 오류를 구분하기

쓰기 뒤 조용한 UART는 주소가 잘못된 주변장치를 선택했거나, 장치가 비활성화됐거나, 송신기가 준비되지 않았음을 뜻할 수 있습니다. STATUS 관찰은 선택된 대상의 준비 상태를 검사할 수 있지만 그 대상이 의도한 UART라는 것까지 증명하지는 못합니다. 자원 범위, 보드 설명, 가능하다면 문서화된 식별 레지스터, 관련 활성화 상태를 비교하세요.

챕터 10은 다음 경계에서 이어집니다: 올바른 장치를 선택한 뒤에도 각 레지스터 접근은 실제로 무엇을 하는가?

## 체크

1. 주어진 맵에서 `sw x12, 0(x10)`와 x10 = `0x10000000`은 무엇을 대상으로 합니까?
   - A) UART 레지스터 사본을 담은 RAM
   - B) UART의 TX_DATA 인터페이스
   - C) CPU 레지스터 x0
   - Answer: B
   - Explanation: 주소 디코딩이 주변장치를 선택하고 그다음 오프셋 0 레지스터를 선택합니다.

2. 송신 쓰기가 유효하기 전에 알아야 하는 사실은? 모두 고르세요.
   - A) 레지스터가 지원하는 너비
   - B) 문서화된 준비/활성화 조건
   - C) 모든 쓰기를 같은 주소 읽기로 검증할 수 있다는 것
   - Answer: A, B
   - Explanation: 마지막 진술은 일반적인 레지스터 보장이 아닙니다.

3. 디코더가 인접한 두 4KB UART 창 사이에서 주소 비트 12를 실수로 무시합니다. `0x10000000`의 UART0과 `0x10001000`의 UART1이 어떻게 별칭이 생기는지 보이세요. 문서화된 스크래치 상태를 쓰는 안전한 실험을 제안하고, 그 실험을 위험하게 만드는 조건을 밝히세요.

4. CPU의 유효 주소, 변환된 물리 주소, 선택된 장치, 장치 기준 오프셋을 구분하는 추적을 작성하세요. 베어메탈 예제에서만 성립한 등치 가정이 무엇인지 설명하세요.

5. Research challenge: Linux Device I/O 문서를 참고하세요. 물리 주소를 포인터로 캐스팅하는 것이 I/O 매핑과 같지 않은 이유를 설명하고, 매핑 속성과 접근자 순서화를 구분하세요.

## 정확성의 경계

이 교육용 인터커넥트에는 단순한 물리 디코더가 있습니다. 실제 플랫폼은 브리지, 접근 제어 검사, 번역된 버스 주소를 더합니다. 허구 UART 맵은 실제 16550이나 다른 보드의 레지스터 명세로 사용해서는 안 됩니다.
