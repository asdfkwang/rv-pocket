# 챕터 20 — 가상 메모리와 Sv39

> **Part V — Memory Becomes Virtual**

## 두 프로그램이 어떻게 같은 주소를 쓸 수 있는가?

챕터 16은 중요한 메커니즘을 숨겼습니다: 프로세스 A와 B는 모두 가상 주소 `0x40403123`를 가리킬 수 있지만 서로 다른 물리 메모리에 도달합니다. 가상 메모리는 명령어가 쓰는 주소를 변환하고 권한을 검사합니다. 프로세스의 물리 페이지가 연속일 필요는 없습니다.

페이지는 매핑과 보호를 위한 고정 크기 영역입니다. 4KB 페이지로 시작하므로 하위 12 주소 비트가 페이지 내 오프셋입니다. 변환은 그 오프셋을 유지하면서 페이지 번호를 바꿉니다. 페이지 테이블이 매핑을 기록하고, 적용 가능한 변환이 아직 캐시되지 않았을 때 MMU가 이를 조회합니다.

우리 예제는 RV64에서 Sv39, user 모드 실행, 4KB 리프로 가는 성공한 3단계 walk를 사용합니다. Sv39는 39개의 의미 있는 가상 주소 비트를 쓰며 64비트 주소의 상위 비트가 비트 38과 일치해야 합니다. 선택한 주소는 낮은 정규 영역에 있습니다.

## 먼저 실제 주소를 분해하기

`VA = 0x0000000040403123`을 변환합니다. 필드는 이렇습니다:

```text
VPN[2] = 1     비트 38:30
VPN[1] = 2     비트 29:21
VPN[0] = 3     비트 20:12
offset = 0x123 비트 11:0

VA = (1 << 30) + (2 << 21) + (3 << 12) + 0x123
```

각 VPN 필드는 9비트이므로 512개 항목 중 하나를 선택합니다. Sv39 페이지 테이블 항목은 8바이트를 차지합니다: `512 * 8 = 4096`. 한 테이블이 4KB 페이지 하나에 들어갑니다. 여러 단계 덕분에 OS는 가능한 모든 가상 페이지에 평면 항목을 할당하는 대신 필요한 영역에 대해서만 하위 테이블을 할당합니다.

## 세 개의 구체적 테이블 따라가기

satp가 Sv39를 선택하고 루트 물리 페이지 `0x81000`을 가리키며 그 기준은 `0x81000000`이라고 가정합니다. 모든 페이지 테이블 메모리는 walker가 접근할 수 있습니다. OS가 다음 항목들을 설치했습니다:

| 테이블 기준 | 인덱스 | 항목의 물리 주소 | 항목 의미 |
| --- | --- | --- | --- |
| `0x81000000` | 1 | `0x81000008` | 유효 비리프, 다음 테이블 `0x81001000` |
| `0x81001000` | 2 | `0x81001010` | 유효 비리프, 다음 테이블 `0x81002000` |
| `0x81002000` | 3 | `0x81002018` | 유효 리프, 물리 페이지 기준 `0x82005000` |

각 단계에서 항목 주소는 `table_base + index * 8`입니다. 다음 테이블에 대한 포인터는 그 항목의 물리 페이지 번호에서 추출하며 인접성에서 추론하지 않습니다. 읽기 쉽게 인접한 테이블 페이지를 골랐지만 RAM에서 인접할 필요는 없습니다.

이 user 읽기/쓰기 매핑에서 리프는 V, R, W, U, A, D가 설정되고 X는 해제된 상태입니다. 각각 유효, 읽기 가능, 쓰기 가능, 사용자 접근 가능, 접근됨, 더티, 실행 불가 상태를 뜻합니다. 두 비리프 항목은 V가 설정되고 R/W/X는 해제됩니다. 첫 성공 walk에서 A/D 갱신 정책을 피하기 위해 A와 D를 미리 설정했습니다.

결과는 `0x82005000 + 0x123 = 0x82005123`입니다. 그 위치에서 읽으면 데이터를 얻습니다. 페이지 테이블 읽기는 매핑 메타데이터를 얻었습니다. 이 두 종류의 읽기를 섞으면 walk 다이어그램을 해석하기 어려워집니다.

## 프로세스가 바뀌면 루트가 바뀐다

프로세스 B는 같은 가상 페이지에 대해 `0x83007000`을 가리키는 리프를 가지는 다른 루트를 가질 수 있습니다. 그러면 같은 VA가 `0x83007123`에 도달합니다. 또는 두 프로세스가 의도적으로 하나의 물리 페이지를 공유하도록 매핑할 수 있습니다. 분리된 주소 공간은 격리와 통제된 공유를 가능하게 합니다. 모든 물리 바이트가 사적일 필요는 없습니다.

필요한 user/읽기/쓰기 권한이 없는 리프에 대한 user 접근은 물리 페이지가 존재해도 거부됩니다. 유효하지 않은 항목이나 금지된 접근은 관련 변환 규칙 아래에서 페이지 폴트를 일으킵니다. OS는 그 접근이 복구 가능한 상황인지 정책 위반인지 결정합니다.

프로그램은 일반적으로 자신의 권한 변환 상태를 직접 고칠 수 없습니다. 챕터 14의 권한 검사가 커널의 매핑 결정을 보호합니다. 챕터 21에서는 캐시된 변환과 fault가 그러한 결정의 변화와 어떻게 상호작용하는지 설명합니다.

## 체크

1. 풀어낸 walk에서 최종 물리 주소는?
   - A) `0x81002018`
   - B) `0x82005123`
   - C) `0x40403123`
   - Answer: B
   - Explanation: 리프가 물리 페이지 기준을 제공하고 원래 VA가 오프셋 `0x123`을 제공합니다.

2. 옳은 진술은? 모두 고르세요.
   - A) 페이지 테이블 항목은 물리 메모리에 저장된 데이터입니다.
   - B) 인접한 가상 페이지는 반드시 인접한 물리 페이지로 매핑되어야 합니다.
   - C) 두 루트가 같은 VA를 다르게 매핑할 수 있습니다.
   - Answer: A, C
   - Explanation: OS가 각 매핑을 선택합니다. 가상 인접성은 물리 인접성을 강제하지 않습니다.

3. 같은 테이블로 `0x40403ABC`를 변환하세요. 그다음 `0x40404123`에 어떤 추가 항목이 필요한지 설명하세요. 바뀌는 인덱스와 그 이유를 보이세요.

4. 리프의 물리 페이지 번호는 유지하고 U를 해제하세요. user load의 결과와, 애플리케이션에서 수치 주소만 바꿔 그 페이지에 대한 권한이 생기지 않는 이유를 설명하세요.

5. Research challenge: Sv39 명세를 사용해 정렬된 영역의 중간 단계에 유효한 2MB 리프를 구성하세요. 어떤 테이블 조회가 사라지고, 더 많은 하위 주소 비트가 오프셋이 되는지, 외견상 유효한 항목이 fault를 일으키게 하는 정렬 규칙은 무엇인지 밝히세요.

## 정확성의 경계

이 추적은 4KB 리프, 유효한 정규 주소, 허용된 페이지 테이블 메모리 접근, 사전 설정된 A/D 비트를 가정합니다. Sv39는 더 큰 리프와 추가 권한 규칙도 지원합니다. TLB는 반복 walk를 피할 수 있지만 매핑의 소프트웨어 관리되는 원천으로 페이지 테이블을 대체하지는 않습니다.
