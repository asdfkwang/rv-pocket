# 챕터 14 — 권한: M, S, U

> **Part IV — Protection and the Operating System**

## 무엇이 애플리케이션이 커널이 되는 것을 막는가?

챕터 13는 트랩으로 권한 소프트웨어에 진입했습니다. 애플리케이션이 핸들러 주소를 자유롭게 바꾸거나 보호를 끌 수 있다면 이 경계는 격리를 제공하지 못합니다. 권한 레벨은 이미 필요한 권한을 가진 소프트웨어에만 일부 연산을 허용합니다.

RISC-V는 machine 모드 M, supervisor 모드 S, user 모드 U를 부릅니다. M이 이들 중 가장 높은 권한입니다. 구현과 실행 환경은 어떤 추가 모드를 지원하는지 다릅니다. 우리 리눅스 중심 기계는 펌웨어를 M-mode에, 커널을 S-mode에, 애플리케이션을 U-mode에 둡니다. 이 배치는 아키텍처가 지원하는 시스템 설계 선택이지 모든 RISC-V 시스템이 리눅스를 한다는 뜻이 아닙니다.

## 허용된 요청과 금지된 연산을 따라가기

user 프로그램이 `A`를 출력하고 싶어합니다. UART의 물리 주소에 쓰는 것은 평범하게 접근 가능한 가상 주소 공간의 일부가 아닙니다. 대신 쓰기 시스템 콜을 발행합니다. 하드웨어가 더 높은 권한 소프트웨어가 설정한 트랩 진입으로 제어를 옮깁니다. 커널은 장치 작업을 요청하기 전에 디스크립터, 버퍼, 권한을 검증합니다.

U-mode가 supervisor 제어 레지스터에 쓰려는 시도와 비교해 보세요. 명령어의 권한 검사가 illegal-instruction 예외로 연산을 거부합니다. CSR 번호를 아는 것만으로 애플리케이션이 supervisor가 되지는 않습니다. 주소나 opcode를 아는 것은 그것을 쓸 권한이 아닙니다.

```text
허용된 경로:
U-mode 요청 -> 트랩 진입 -> 커널 검증 -> 권한 있는 장치 연산

금지된 지름길:
U-mode CSR 쓰기 -> 권한 검사 실패 -> 예외 처리
```

허용된 경로에는 정책 결정이 포함됩니다. 시스템 콜은 요청이지 요청된 동작이 반드시 승인된다는 보장이 아닙니다. 커널은 장치를 건드리지 않고 에러를 반환할 수 있습니다.

## 어느 계층이 어떤 메커니즘을 통제하는가?

supervisor는 애플리케이션의 페이지 테이블을 관리하고 S-mode 트랩 레지스터를 씁니다. 펌웨어는 machine 수준 기능을 유지하고 정의된 인터페이스로 선택된 서비스를 노출할 수 있습니다. 기계 소프트웨어는 위임을 설정해 특정 트랩을 supervisor가 직접 처리하게 합니다. 위임은 모드 간 구분을 없애거나 사용자가 임의의 진입 코드를 선택하게 하지 않습니다.

메모리 격리는 현재 모드만의 문제가 아닙니다. 변환 권한, 구성된 경우 물리 메모리 보호, 장치/인터커넥트 접근 제어도 접근을 제약할 수 있습니다. 반대로 권한 있는 커널 코드에도 유효하지 않은 포인터나 순서화 버그가 있을 수 있습니다. 권한은 허용된 연산을 확장할 뿐 그 정확성을 확립하지 않습니다.

트랩 복귀 명령어는 저장된 상태를 사용해 적절한 모드와 재개를 복원합니다. 일반 레지스터를 통해 점프하는 평범한 함수 반환과는 바꿔 쓸 수 없습니다. user에서 커널로의 전이를 단순한 함수 호출로 보는 것은 권한 변화와 특수한 진입/종료 책임을 모두 놓칩니다.

## 커널 서비스와 펌웨어 서비스 분리하기

S-mode 드라이버가 M-mode가 통제하는 기능이 필요하다고 합시다. 기계 CSR에 직접 접근하면 supervisor 권한이 부족해 trap될 수 있습니다. 해결책은 플랫폼 계약에 달려 있습니다: 커널은 SBI 서비스를 쓸 수 있고, 위임된 아키텍처 기능을 쓸 수 있고, 플랫폼 드라이버 인터페이스를 쓸 수 있습니다. CSR 접근을 추측하는 것은 그 계약을 발견하는 대신이 되지 못합니다.

챕터 25에서 구체적인 레지스터와 함께 SBI 호출을 따라갑니다. 지금은 두 요청을 구분하세요: 사용자 시스템 콜은 OS에 서비스를 요청하는 것이고, SBI 호출은 더 낮은 수준의 실행 환경에 서비스를 요청하는 것입니다. 둘 다 ecall을 쓸 수 있지만 출발 모드, 인자, 핸들러가 다릅니다.

다음 장은 이 메커니즘 위에 OS 정책을 쌓습니다. 하드웨어는 경계를 강제할 수 있지만, 소프트웨어는 어떤 프로세스가 파일을 소유하는지, 어떤 연산이 허용되는지, 성공한 요청이 무슨 뜻인지를 결정합니다.

## 체크

1. U-mode 명령어가 권한 없는 supervisor CSR 쓰기를 시도합니다. 어떤 결과가 권한 경계에 부합합니까?
   - A) CSR 번호를 아면 접근이 허가된다.
   - B) 연산이 illegal-instruction 예외를 발생시킨다.
   - C) 자동으로 성공한 시스템 콜이 된다.
   - Answer: B
   - Explanation: 권한 검사는 명령어에 적용됩니다. 권한 없는 접근을 승인된 요청으로 재해석하지 않습니다.

2. 선택한 리눅스 중심 배치에 대해 옳은 진술을 모두 고르세요.
   - A) 커널 S-mode는 애플리케이션 U-mode보다 높은 권한입니다.
   - B) 모든 RISC-V 구현이 이 소프트웨어 배치를 실행해야 합니다.
   - C) 커널 서비스는 올바르게 전달된 요청을 거부할 수 있습니다.
   - Answer: A, C
   - Explanation: 하드웨어 전달과 OS 인가는 별개이며, 그 소프트웨어 배치는 보편적이지 않습니다.

3. U-mode의 트랩 벡터 레지스터 쓰기를 막는 것이 왜 중요한지 설명하세요. 애플리케이션이 커널 진입 주소를 자신의 코드로 바꿔 권한을 가진 채 진입할 수 있다면 격리가 어떻게 깨지는지 구성하세요.

4. 드라이버가 CSR 연산에서 illegal-instruction trap을 봅니다. 지원되지 않는 CSR와 권한 부족을 구분하는 진단을 제안하세요. 펌웨어 서비스를 대체책으로 선택하기 전에 필요한 증거를 명시하세요.

5. Research challenge: machine 수준 위임 레지스터와 supervisor 복귀 규칙을 살펴보세요. 위임할 수 있는 경우 하나를 찾고, 위임이 supervisor 소프트웨어가 기계 CSR에 접근할 수 있는 일반적인 허가가 아닌 이유를 설명하세요.

## 정확성의 경계

하이퍼바이저 가상화, 상세한 PMP 구성, 선택적 권한 확장은 생략합니다. 메모리 권한은 챕터 20~21에서 다룹니다. 특정 명령어나 자원에 접근 가능한지는 이름뿐 아니라 구성된 환경에 달려 있습니다.
