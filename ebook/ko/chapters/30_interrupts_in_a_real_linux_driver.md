# 챕터 30 — 실제 리눅스 드라이버에서의 인터럽트

> **Part VII — Linux Device Drivers**

## 리눅스 핸들러는 무엇에 책임이 있는가?

챕터 12는 하드웨어 알림과 트랩 진입을 따라갔습니다. 리눅스 IRQ 서브시스템은 장치의 인터럽트 자원을 핸들러에 연결합니다. 리눅스 IRQ 번호는 커널이 관리하는 식별자이며 디바이스 트리 cell이나 인터럽트 컨트롤러의 원시 소스 번호와 반드시 같지 않습니다.

probe는 버스/플랫폼 인터페이스를 통해 적절한 IRQ를 얻고 인스턴스 포인터와 함께 핸들러를 등록합니다. 핸들러는 자신의 장치에 관련 대기 작업이 있는지 식별하고, 이를 처리하거나 안전하게 미루고, 적절한 결과를 반환해야 합니다. 공유 라인에서는 다른 장치가 서비스를 요청했기 때문에 핸들러가 호출될 수 있습니다.

## 제한 있는 수신 서비스 따라가기

챕터 10의 교육용 UART 래치된 수신 이벤트와 재단언 규칙을 사용합니다. 다음은 리눅스 방식 호출을 사용하는 프로토콜 스케치입니다. `queue_byte_irqsafe`는 명시적인 오버플로 정책과 함께 제한이 있는 비수면 소프트웨어 큐 연산을 나타냅니다:

```c
u32 pending = readl(d->base + IRQ_STATUS) & RX_EVENT;
if (!pending)
    return IRQ_NONE;

for (unsigned int n = 0; n < 32; n++) {
    if (!(readl(d->base + STATUS) & RX_READY))
        break;
    u8 byte = readl(d->base + RX_DATA) & 0xff;
    queue_byte_irqsafe(d, byte);
}
writel(RX_EVENT, d->base + IRQ_STATUS);
wake_up_interruptible(&d->readers);
return IRQ_HANDLED;
```

반복 예산이 한 번 호출의 작업을 제한합니다. 우리의 장치는 확인 후 읽지 않은 데이터가 남으면 수신 이벤트를 재단언하므로, 예산에서 멈춰도 FIFO가 비었다고 선언하지 않습니다. 실제 하드웨어는 마스킹과 지연된 비우기를 요구할 수 있습니다. 실제 프로토콜을 사용하세요.

큐는 하드웨어 이벤트의 수명 너머로 데이터를 기록합니다. 웨이크업은 기다리는 소비자가 조건을 다시 검사할 수 있게 합니다. 큐잉된 바이트를 사용자의 버퍼로 직접 옮기거나 소비자가 즉시 실행된다고 보장하지는 않습니다.

IRQ_NONE은 이 핸들러가 처리할 관련 원인을 찾지 못했다는 뜻입니다. 하드웨어를 지우지 않으며 범용 에러 보고 메커니즘도 아닙니다. 소스를 처리하거나 관리하지 않은 채 IRQ_HANDLED를 반환하면 레벨 민감 조건이 CPU를 반복적으로 인터럽트할 수 있습니다.

## 컨텍스트가 구현을 제약한다

하드드 IRQ 핸들러는 임의의 수면 작업을 수행할 수 없습니다. 사용자 메모리 접근, 블로킹 락, 수면 할당은 이 경로에 부적합합니다. 결과를 작은 큐에 넣어 나중에 소비하게 하는 것이 급한 장치 서비스와 잠재적으로 블로킹 연산을 분리합니다.

스레드 IRQ는 다른 배치입니다: 주 핸들러가 소스를 식별하고 관리하고, 프레임워크 규칙 아래 수면 가능한 작업을 수행할 스레드를 요청할 수 있습니다. IRQF_ONESHOT과 장치 마스킹은 구체적 의미를 가집니다. 무엇이 소스를 주장 상태로 유지하는지, 제거가 활동을 어떻게 동기화하는지 알아야 한다는 필요를 없애지 않습니다.

인터럽트 핸들러의 반환은 하위 수준 트랩 진입이 인터럽트된 상태를 저장한 뒤 훨씬 뒤에 일어납니다. 드라이버는 아키텍처의 완전한 레지스터 저장 수열을 C 콜백에서 수동으로 재현해서는 안 됩니다. 그 책임은 커널 진입/IRQ 프레임워크에 있습니다.

## 시작 경로와 함께 정지 경로 설계하기

제거 중에 필요하면 새 하드웨어 요청을 막고, 진행 중인 IRQ 실행을 동기화하고, 핸들러가 큐잉한 작업을 비운 뒤 그 상태를 해제해야 합니다. IRQ만 동기화하는 것으로 핸들러가 앞서 예약한 워커가 취소되지는 않습니다.

같은 순서가 IRQ 등록 뒤 probe가 실패할 때도 중요합니다. 자동 관리형 IRQ 해제는 독립적으로 대기 중인 작업 항목에 안전한 해제된 큐를 만들지는 못합니다. 인스턴스의 모든 비동기 사용자를 추적하고 각각이 더 이상 실행될 수 없는 시점을 확립하세요.

핸들러가 실행되지 않는다면 대기 중인 장치 상태, 장치 활성화, 라우팅, 리눅스 IRQ 등록, CPU 전달을 조사하세요. 반복 실행된다면 소스 서비스와 확인을 조사하세요. 한 번 실행되는데도 리더가 블로킹된다면 챱터 31에서 다룬 소프트웨어 공개/웨이크업 경로를 살펴보세요.

## 체크

1. 공유 라인에서 이 장치가 관련 원인을 보고하지 않습니다. 핸들러는 보통 무엇을 반환해야 합니까?
   - A) IRQ_NONE
   - B) IRQ_HANDLED를 반환하며 무관한 장치 상태를 지운다
   - C) 뮤텍스에서 자라는 요청
   - Answer: A
   - Explanation: 공유 라인 분배는 각 핸들러가 자신의 장치가 서비스를 필요로 하는지 판단하게 요구합니다.

2. 단순히 IRQ_HANDLED를 반환하는 것 외에 어떤 의무가 있습니까? 모두 고르세요.
   - A) 실제 장치 원인을 처리하거나 관리한다.
   - B) 핸들러의 실행 컨텍스트를 존중한다.
   - C) 비동기 상태가 살아 있게 한다.
   - Answer: A, B, C
   - Explanation: 반환값은 프로토콜, 컨텍스트 안전, 자원 수명을 구현하지 않습니다.

3. 진입 시 40바이트가 대기 중이라고 합시다. 명시된 예산과 재단언 규칙 아래 두 번의 호출을 추적하세요. 소프트웨어 큐가 16바이트만 담을 수 있다면 어떤 추가 상태가 필요한지 설명하세요.

4. 작업을 큐잉하는 IRQ 핸들러가 관련된 제거 경합을 그리세요. synchronize_irq만으로 장치 객체를 쓰는 모든 콜백이 끝났다고 확립되지 않는 이유를 식별하세요.

5. Research challenge: `request_threaded_irq`와 IRQF_ONESHOT 문서를 살펴보세요. 선택한 장치 프로토콜에 대해 어떤 작업이 주 핸들러에 남고 어떤 작업이 스레드에서 실행될 수 있는지 설명하세요. 소스 마스킹과 teardown 가정을 포함하세요.

## 정확성의 경계

이 핸들러는 기호적 오프셋, 생략된 큐 구현, 허구 이벤트 프로토콜을 쓴 교육용 조각입니다. 실제 직렬 드라이버는 보통 독립적인 수신 인터페이스를 도입하는 대신 serial 서브시스템과 통합합니다. 커널 구성은 인터럽트와 락 컨텍스트를 바꿀 수 있습니다.
