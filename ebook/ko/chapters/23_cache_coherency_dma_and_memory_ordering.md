# 챕터 23 — 캐시 일관성, DMA, 그리고 메모리 순서

> **Part V — Memory Becomes Virtual**

## DMA가 오래된 데이터를 볼 때 빠진 보장은 무엇인가?

챕터 22에서 소유권 전이를 소개했습니다. "DMA가 오래된 메모리를 읽었다"처럼 보이는 서로 다른 세 가지 실패가 있습니다: 장치가 오래된 캐시 사본을 보거나, 필드를 잘못된 순서로 관찰하거나, CPU가 바꾸는 중에 버퍼에 접근합니다. 캐시 가시성, 순서화, 소유권은 각각 따로 추론해야 합니다.

일관적인 DMA 메모리는 CPU와 장치 사이에 정의된 공유 가시성 배치를 제공합니다. CPU 저장 수열을 분할 불가로 만들거나 모든 장치 요구 공개 순서를 자동으로 강제하지는 않습니다. 스트리밍 매핑은 명시적인 장치/CPU 소유권 전이와 플랫폼에서 요구하는 동기화를 갖는 생명주기를 제공합니다.

## 일관적인 디스크립터를 올바른 순서로 공개하기

일관적인 DMA 메모리로 할당한 디스크립터 링을 가정합니다. 장치는 OWN 플래그를 관찰하고 OWN = 1을 보면 주소를 읽을 수 있습니다. 처음에 디스크립터는 오래된 주소, 길이 0, OWN = 0을 담습니다.

리눅스 방식의 개념적 공개는 이렇습니다:

```c
/* 디스크립터 레이아웃/엔디언 변환은 장치별로 다르므로 생략합니다. */
desc->address = payload_dma;
desc->length = 16;
dma_wmb();
WRITE_ONCE(desc->own, 1);
/* 필요하면 문서화된 MMIO 접근자/프로토콜로 알립니다. */
```

이 배리어는 이 DMA 공유 패턴에서 앞선 디스크립터 쓰기와 소유권 공개 사이에 필요한 순서를 확립합니다. 그것이 없으면 장치는 OWN = 1을 새 길이나 주소가 필요한 순서로 보이기 전에 볼 수 있습니다. 일관성은 가시성 참여를 보장하고, 배리어는 관찰 사이의 관계를 표현합니다.

이것은 프로토콜 조각입니다. 디스크립터의 플래그 너비, 엔디언 형식, 장치 보장, 도어벨 순서는 모두 실제 하드웨어와 일치해야 합니다. WRITE_ONCE는 컴파일러 접근을 제약할 뿐 DMA 동기화 계약 전체를 독립적으로 제공하지 않습니다.

완료 시 일부 장치는 결과 필드를 쓴 뒤 OWN을 해제합니다. 그 계약이 그 순서를 보장한다면 CPU는 소유권 복귀를 관찰하고 적절한 DMA 읽기 배리어를 쓴 뒤 결과 필드를 소비할 수 있습니다. 소프트웨어 배리어가 하드웨어가 결코 약속하지 않은 완료 순서를 보상할 수는 없습니다.

## 스트리밍 버퍼를 소유자 사이에서 옮기기

이제 비일관적 머신에서 별도로 매핑된 페이로드를 생각해 봅시다. 디스크립터 순서를 준비하는 것이 더티 페이로드 캐시 라인을 반드시 클리닝하지는 않습니다. 디스크립터 공개에 더해 페이로드에도 DMA API의 매핑/동기화 생명주기를 사용하세요.

지속적인 수신 매핑에 대해 전형적인 개념적 사이클은 이렇습니다:

```text
장치가 버퍼를 소유하고 페이로드를 씀
완료가 장치가 더 이상 이 버퍼에 접근하지 않음을 확립
dma_sync_single_for_cpu(..., DMA_FROM_DEVICE)
CPU가 완료된 바이트를 읽음
dma_sync_single_for_device(..., DMA_FROM_DEVICE)
재제출 후 장치가 다시 버퍼를 소유할 수 있음
```

매핑을 재사용하지 않고 종료하는 경우 해당 unmap 연산이 매핑 종료에 필요한 전이를 수행합니다. 방향 불일치는 무해한 최적화 힌트가 아닙니다. 플랫폼은 허용된 접근과 필요한 유지보수를 결정하는 데 방향을 사용합니다.

장치가 스트리밍 버퍼를 소유하는 동안 CPU는 같은 캐시 라인에 무관한 데이터를 쓰면 안 됩니다. 캐시 유지보수는 라인 단위로 작동하므로 careless한 공유는 명목상 바이트 범위가 달라도 이웃 데이터를 덮어쓰거나 무효화할 수 있습니다. DMA API가 지원하는 할당과 정렬 규칙을 사용하세요.

## fence와 캐시 유지보수를 혼동하지 말라

순서 fence는 연산 종류들이 서로에 대해 관측될 수 있는 시점을 제약합니다. 캐시 유지보수는 캐시 사본의 상태를 정렬합니다. 변환 동기화는 캐시된 매핑에 관한 것입니다. 세 연산은 같은 메모리를 다룰 수 있지만 서로 다른 문제를 풉니다.

CPU 메모리 배리어는 사용자 공간 포인터를 DMA 주소로 바꾸지 않습니다. SFENCE.VMA는 더티 페이로드 바이트를 비일관적 장치에 공개하지 않습니다. 데이터 flush는 타임아웃된 DMA 엔진이 멈췄다는 것을 증명하지 못합니다. 수정을 제안할 때 API를 고르기 전에 관측자와 빠진 보장을 밝히세요.

다음 Part는 리눅스가 실행되기 전에 시작해, 펌웨어가 이 모든 메커니즘을 쓸 수 있는 환경을 어떻게 확립하는지 묻습니다. 챕터 32에서 DMA API와 완전한 생명주기로 돌아옵니다.

## 체크

1. 일관적인 디스크립터의 OWN 플래그가 새 길이보다 먼저 보입니다. 직접 관련된 빠진 보장은?
   - A) 공개 순서
   - B) 버퍼의 가상 주소가 수치적으로 작다는 것
   - C) 캐시 라인이 반드시 없다는 것
   - Answer: A
   - Explanation: 일관적인 가시성은 필드와 소유권 사이에 필요한 순서 관계를 대체하지 않습니다.

2. 옳은 주장은? 모두 고르세요.
   - A) 배리어는 타임아웃 후 엔진이 멈췄음을 증명한다.
   - B) DMA 동기화 방향은 접근 계약의 일부입니다.
   - C) 겹치지 않는 바이트 범위에서도 캐시 라인 공유가 중요할 수 있습니다.
   - Answer: B, C
   - Explanation: 수명에는 완료 또는 정지 상태가 필요하고, 캐시 유지보수는 라인 전체에 영향을 줄 수 있습니다.

3. 오래된 페이로드 바이트와 너무 일찍 공개된 디스크립터 소유권에 대해 각각 실패 타임라인을 그리세요. 디스크립터 배리어만 고쳐도 페이로드 경우가 반드시 해결되지 않는 이유를 설명하세요.

4. 지속적인 스트리밍 매핑을 위한 반복 수신 사이클을 설계하세요. 각 소유권 전이를 표시하고, 매 완료된 전송마다 버퍼를 unmap하는 경우 어떤 연산이 사라지거나 바뀌는지 식별하세요.

5. Research challenge: 커널 메모리 배리어 문서와 DMA 가이드에서 dma_wmb/dma_rmb 사용을 살펴보세요. 한 예제를 올바르게 만드는 가정된 장치 동작을 밝히고, 그 배리어가 제공하지 않는 보장을 식별하세요.

## 정확성의 경계

이 코드 조각은 프로토콜 스케치이며 보편적인 링 구현이 아닙니다. 실제 하드웨어가 완료 가시성, 도어벨 동작, 캐시 정렬, 엔디언 필드를 정의합니다. 임의의 RISC-V fence나 캐시 명령을 대신 쓰지 말고 대상 플랫폼의 커널 DMA 및 I/O API를 사용하세요.
