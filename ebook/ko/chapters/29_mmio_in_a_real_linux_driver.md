# 챕터 29 — 실제 리눅스 드라이버에서의 MMIO

> **Part VII — Linux Device Drivers**

## 자원은 어떻게 레지스터 접근이 되는가?

챕터 09는 베어메탈 추적에서 물리 주소를 직접 썼습니다. 챕터 28은 리눅스 매핑을 얻었습니다. 이제 쉽게 혼동되는 세 가지 양을 따라갑니다: 장치 자원의 물리/버스 주소, 커널의 I/O 매핑 토큰, 자원 안에서 레지스터의 바이트 오프셋.

교육용 UART 자원이 물리 `0x10000000`에서 시작해 `0x1000`바이트에 걸쳐 있다고 가정합니다. 플랫폼 매핑 도구가 `void __iomem *base`를 제공합니다. 그 수치 표현이 `0x10000000`과 같을 필요는 없습니다. 평범한 C 메모리가 아니라 적절한 접근자와 함께 쓸 I/O 매핑으로 다루세요.

## 문서화된 너비로 바이트 하나 전송하기

챕터 09는 정렬된 32비트 리틀 엔디안 레지스터 접근을 명시했고, TX_DATA는 오프셋 0, STATUS는 오프셋 4에 있습니다. 다음 조각은 probe가 이미 장치를 매핑하고 활성화했으며, 접근이 직렬화되고, 이 호출이 수면 가능한 컨텍스트에 있다고 가정합니다:

```c
u32 status;
int ret;

ret = readl_poll_timeout(base + 0x04, status,
                         status & BIT(0), 10, 1000);
if (ret)
    return ret;
writel(0x41, base + 0x00);
```

이 리눅스 방식 조각은 폴링 도구로 문서화된 준비 비트를 기다린 다음 바이트 값을 담은 32비트 쓰기를 수행합니다. 도구의 지연과 타임아웃 인자는 마이크로초 단위이며, 실제 스케줄링이 관찰 시간에 영향을 줍니다. 커널의 GNU C 환경은 이 void 포인터에서 바이트 단위 산술을 허용합니다. 이식이 이식 가능한 ISO C에 대한 약속은 아닙니다.

레지스터 경계에서 오프셋 4는 커널 매핑의 수치 기준과 관계없이 STATUS를 선택합니다. `u32 *`를 쓰고 4를 더했다면 대신 4개 원소, 보통 16바이트만큼 전진합니다. 잘못된 포인터 산술 단위는 모든 값이 그럴듯하게 정렬되어 보이면서도 다른 레지스터를 선택할 수 있습니다.

raw 역참조는 완전한 리눅스 MMIO 계약을 담고 있지 않습니다. 접근자 선택은 너비, 엔디언 해석, 아키텍처에 적합한 I/O 동작을 표현합니다. 바이트 접근이나 빅 엔디안 레지스터를 요구하는 다른 장치에는 그에 대응하는 접근자가 필요합니다. 동작을 결정하는 것은 교육용 UART의 계약이지 CPU 레지스터 너비가 아닙니다.

## 순서가 지켜져도 완료된 것은 아닙니다

일부 버스는 쓰기를 post합니다: CPU에 보이는 쓰기 연산이 주변장치가 소비하기 전에 끝날 수 있습니다. 프로토콜이 다음 단계 전에 도착을 요구한다면 같은 장치/경로의 적절한 레지스터에서 문서화된 읽기가 앞서 post된 쓰기를 flush하기 위해 필요할 수 있습니다. 그 읽기 자체도 버스에 대해 안전하고 적절해야 합니다.

RX_DATA를 아무 데나 읽어 오는 데 쓰지 마세요. 바이트를 소비하기 때문입니다. 쓰기 전용 명령 레지스터가 쓰여진 값을 반환한다고 가정하지도 마세요. 명령 전달의 flush와 명령된 연산의 완료를 기다리는 것을 혼동하지도 마세요: 리셋 명령을 받았다고 리셋 완료 상태가 나타나기 전에 시간이 필요할 수 있습니다.

이 구분이 세 경계 추적에서 보입니다:

```text
CPU가 명령 발행 -> 인터커넥트가 명령 전달 -> 장치가 연산 완료
```

배리어나 접근자 순서 보장은 명시된 순서 관계를 다룹니다. 안전한 readback은 버스 계약 아래 전달을 확립할 수 있습니다. 완료 상태나 인터럽트는 더 나중의 장치별 경계를 확립합니다. 다음 명령어가 어떤 보장에 의존하는지 밝히세요.

## 직렬화는 여전히 드라이버의 몫입니다

두 호출자가 독립적으로 TX-ready를 폴링하고 둘 다 그것이 설정된 것을 쓰기 전에 관찰했다고 합시다. 첫 쓰기가 사용 가능한 슬롯을 소비하면 두 번째는 장치 프로토콜 아래 무효가 됩니다. 폴링 접근자가 검사-제출 수열 전체를 배타적으로 만들지는 않았습니다. 드라이버는 실행 컨텍스트와 하드웨어 용량에 맞는 큐잉이나 직렬화가 필요합니다.

마찬가지로 readl/writel은 잘못된 W1C 마스크나 잘못된 자원 설명을 고치지 않습니다. 그들은 API 계약 아래 접근을 구현할 뿐 레지스터 프로토콜은 작성자의 책임으로 남습니다.

챕터 30은 이 폴링 경로를 알림으로 대체하고 인터럽트 핸들러의 제한된 실행 컨텍스트를 추적합니다.

## 체크

1. 매핑된 기준이 자원의 물리 시작과 수치적으로 다릅니다. STATUS는 어디에 접근합니까?
   - A) 매핑을 통해 바이트 오프셋 `0x04`에서
   - B) 물리 `0x10000004`를 평범한 포인터로 캐스팅해서
   - C) 평범한 타입 포인터에 u32 4개를 더해서
   - Answer: A
   - Explanation: 매핑과 바이트 오프셋이 적절한 I/O 접근을 정의합니다.

2. 어떤 구분이 필요한가? 모두 고르세요.
   - A) 명령 전달 대 장치 완료
   - B) 안전한 상태 readback 대 데이터를 소비하는 읽기
   - C) CPU 레지스터 너비 대 장치 접근 너비
   - Answer: A, B, C
   - Explanation: 이들은 독립적인 인터페이스 속성입니다. 하나를 다른 것에서 추론할 수 없습니다.

3. 두 호출자의 TX-ready 경합을 그리세요. 직렬화 스킴을 제안하고, 수면 가능한 폴링 도구 너머에 스핀락을 잡고 있는 것이 왜 그 컨텍스트 요구를 위반하는지 설명하세요.

4. 명령이 post되고 소프트웨어가 즉시 선행 클럭을 비활성화합니다. 빠진 보장을 설명하고, 클럭 종료 전에 명령 도착과 필요시 완료를 확립하는 장치별 순서를 설계하세요.

5. Research challenge: 리눅스 문서에서 readl/writel, relaxed 변형, 빅 엔디안 접근자를 비교하세요. 다른 접근자로 대체하면 잘못되게 만드는 구체적인 순서 또는 형식 가정 하나를 밝히세요.

## 정확성의 경계

이 조각은 완전한 직렬 드라이버가 아닙니다. 프레임워크 통합, 전원 관리, teardown를 생략합니다. 준비와 너비 규칙은 허구 UART에 속합니다. Post 쓰기 flush와 순서 세부사항은 대상 버스와 접근자 계열에 대해 확인해야 합니다.
