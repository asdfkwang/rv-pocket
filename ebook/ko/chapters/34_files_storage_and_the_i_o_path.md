# 챕터 34 — 파일, 저장장치, 그리고 I/O 경로

> **Part VIII — A Complete System**

## 파일 쓰기는 언제 지속되는가?

챕터 33은 수락과 완료를 분리했습니다. 일반 파일 I/O는 또 하나의 경계를 추가합니다: 크래시나 전원 손실 후의 지속성입니다. 커널 버퍼에 복사된 바이트는 저장장치가 그것을 지속하게 만들기 훨씬 전부터 이후 읽기에 보일 수 있습니다.

이미 열린 일반 파일에 대한 평범한 버퍼링 쓰기를 생각해 봅시다. 가상 파일 시스템 계층이 요청을 파일 시스템으로 분배합니다. 데이터가 페이지 캐시(파일 내용을 캐시하는 메모리)로 복사되고 관련 페이지가 dirty로 표시됩니다. writeback이 나중에 파일 시스템과 블록 스택을 통해 저장 요청을 만듭니다. 모든 쓰기가 이 경로를 쓰지는 않습니다: 장치 파일, 직접 I/O, 다른 모드는 다른 계약을 가집니다.

## 저장장치를 통해 바이트 하나 추적하기

애플리케이션의 파일 오프셋 100에 있는 바이트가 `0x41`에서 `0x42`로 바뀐다고 합시다.

| 경계 | 페이지 캐시 값 | 지속 저장장치 값 | 확립되는 것 |
| --- | --- | --- | --- |
| 쓰기 전 | `41` 또는 캐시되지 않음 | `41` | 이전 파일 내용 |
| 버퍼링 쓰기 수락 | `42`, dirty | `41`일 수 있음 | 새 데이터가 메모리에서 수락됨 |
| Writeback 제출 | `42` | 완료 대기 | 저장 작업 요청됨 |
| 필요한 지속성 연산이 성공적으로 완료 | `42` | 저장장치 계약 아래 `42` | 요청된 동기화가 확립됨 |

파일 캐시를 통한 읽기는 두 번째 행에서 `42`를 반환할 수 있습니다. 그 성공적인 읽기는 전원 손실 지속성을 증명하지 않습니다. 마찬가지로 I/O 완료는 장치의 휘발성 쓰기 캐시와 파일 시스템의 지속성 프로토콜을 고려해야 더 강한 보장이 만족될 수 있습니다.

fsync는 문서화된 계약 아래 파일의 데이터와 필요한 메타데이터를 동기화해 달라고 시스템에 요청합니다. 애플리케이션은 그 결과를 확인해야 합니다: 에러는 초기 쓰기보다 나중에 보고될 수 있습니다. close는 명시적 지속성 동기화의 일반적 대용이 아닙니다.

## 파일 내용과 그 이름은 서로 다른 상태입니다

애플리케이션이 새 임시 파일을 쓰고 그것을 rename해 설정 파일을 교체한다고 합시다. 새 파일의 바이트와 그것을 가리키는 디렉터리 항목은 서로 다른 영속 객체입니다. 개념적 로컬 파일 시스템 갱신 순서는 이렇습니다:

```text
대상 디렉터리에 임시 파일 생성
새 전체 내용을 쓰며 부분 쓰기 처리
임시 파일을 fsync하고 성공 확인
그 이름 위로 rename하고 성공 확인
포함 디렉터리를 fsync하고 성공 확인
```

이 패턴은 파일 내용과 네임스페이스 갱신을, 필요한 연산과 보장을 지원하는 파일 시스템 아래에서 별도로 다룹니다. 어떤 반환값을 무시해도 되는 근거가 되지 않으며, 파일 시스템 간 rename 규칙이나 애플리케이션 자체 동시성 프로토콜도 면제받지 않습니다.

rename 전에 크래시가 발생하면 임시 파일의 데이터가 동기화되어도 이전 이름은 여전히 이전 파일을 가리킬 수 있습니다. rename 후지만 디렉터리 동기화 전에 크래시가 발생하면 애플리케이션은 아직 의도한 전체 지속성 순서를 끝내지 못했습니다. 인쇄된 "저장 완료" 메시지가 저장 현실을 기술한다고 가정하지 말고 경계마다 추론하세요.

## 저장 스택은 결국 장치에 도달합니다

파일 시스템 아래에서 요청은 큐에 들어가고 합쳐지며 DMA로 전송될 수 있습니다. 챕터 32의 버퍼 수명과 완료 규칙이 그 하위 경로 안에서 적용됩니다. 파일 시스템은 고립된 raw DMA 전송이 담지 못하는 메타데이터와 순서 관계도 관리합니다.

데이터를 잃는 것을 진단하려면 블록 장치를 한 번 관찰하는 것으로는 부족합니다. 애플리케이션이 지속성을 요청했는지, 모든 관련 호출이 성공했는지, 어떤 파일과 디렉터리가 동기화되었는지, 파일 시스템·장치·백킹 플랫폼이 어떤 보장을 제공하는지 확인해야 합니다. 고장 난 장치나 원격 파일 시스템이 조사를 바꿀 수 있지만, 증거 없이 원인으로 단정하지 않습니다.

챕터 35는 입력 이벤트를 반대 방향으로, 물리적 동작에서 커널을 거쳐 애플리케이션까지 따라갑니다. 두 경로 모두 중간 수락과 사용자의 최종 관찰을 구별해야 합니다.

## 체크

1. 버퍼링 쓰기가 성공하고 이후 캐시된 읽기가 새 바이트를 반환합니다. 무엇이 증명됐습니까?
   - A) 읽기 경로가 새 데이터를 관찰할 수 있다.
   - B) 갑작스러운 전원 손실이 새 데이터를 잃지 않는다.
   - C) 포함 디렉터리가 동기화되었다.
   - Answer: A
   - Explanation: 캐시된 가시성은 그 자체로 저장 지속성이나 네임스페이스 지속성을 확립하지 않습니다.

2. 지속적인 교체 파일 프로토콜에서 고려해야 하는 것은? 모두 고르세요.
   - A) 부분 쓰기와 오류
   - B) 파일 데이터 동기화
   - C) 디렉터리 갱신의 지속성
   - Answer: A, B, C
   - Explanation: 세 가지 모두 의도한 갱신이 불완전한 채 남을 수 있는 서로 다른 방법을 나타냅니다.

3. 교체 순서에서 가능한 크래시 지점을 표시하세요. 각각에 대해 어떤 연산이 완료되었고, 파일 시스템 보장을 만들어 내지 않고 보수적으로 주장할 수 있는 것이 무엇인지 밝히세요.

4. 애플리케이션이 fsync 결과를 확인하기 전에 "saved"를 로그합니다. write가 전체 바이트 수를 반환했는데도 로그가 오해를 부르는 실행을 구성하세요. 진단에 필요한 증거를 식별하세요.

5. Research challenge: 선택한 운영체제/파일 시스템의 write, fsync, rename 문서를 참고하세요. 디렉터리 동기화와 장치 쓰기 캐시 동작이 의도한 실패 모델에 어떤 영향을 주는지 설명하고, 지원되지 않는 연산이나 보장을 기록하세요.

## 정확성의 경계

주 추적은 평범한 버퍼링 일반 파일 I/O를 가정합니다. 직접 I/O, 네트워크 파일 시스템, 저널, copy-on-write 파일 시스템, 저장장치 하드웨어는 추가 계약을 가집니다. 지속성은 선택한 스택과 실패 모델에 대해, 모든 관련 오류를 확인하며 주장해야 합니다.
