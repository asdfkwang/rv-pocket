# 챕터 17 — 스레드와 스케줄링

> **Part IV — Protection and the Operating System**

## 두 번째 스레드는 무엇을 공유하는가?

챕터 16은 하나의 실행 흐름을 다른 것으로 전환하는 것을 설명했습니다. 프로세스는 주소 공간과 프로세스 자원을 공유하면서 자체 실행 레지스터와 스택을 유지하는 여러 스레드를 담을 수 있습니다. 공유는 데이터를 복사하거나 명시적으로 주고받을 필요를 줄이지만, 한 스레드의 쓰기가 불편한 시점에 실행될 수 있는 코드에 보인다는 문제를 만듭니다.

스택은 관례와 수명 관리에 따라 한 스레드에 속하며 일반적으로 같은 주소 공간의 다른 스레드로부터 보호되지 않습니다. 스택 객체의 포인터를 전달하면 다른 스레드가 그것에 접근할 수 있습니다. 객체의 수명과 동기화는 프로그램의 책임으로 남습니다.

## 실행 가능, 실행 중, 블로킹 상태 따라가기

하나의 CPU에 스레드 A와 B가 있다고 합시다. A는 입력을 파싱하고 B는 장치 결과를 기다립니다. 실행 중은 현재 CPU를 쓰고 있다는 뜻입니다. 실행 가능은 선택되면 실행될 수 있다는 뜻입니다. 블로킹은 CPU 시간을 두고 경쟁하는 대신 조건이나 이벤트를 기다린다는 뜻입니다.

| 이벤트 | A | B | CPU |
| --- | --- | --- | --- |
| 초기 상태 | 실행 중 | 결과에 블로킹 | A |
| 장치 결과 도착 | 실행 중 | 실행 가능으로 전환 | A 또는 인터럽트 서비스 |
| 스케줄러가 B 선택 | 실행 가능 | 실행 중 | B |
| B가 결과 소비 후 다시 대기 | 실행 가능 | 블로킹 | A 재개 가능 |

B를 깨우는 것은 적격성을 바꿉니다. 즉시 실행을 보장하지도, 장치가 끝난 바로 그 순간 CPU를 B에게 넘기지도 않습니다. I/O 지연을 측정할 때 이 구분이 결정적입니다: 장치 완료, 웨이크업, 실제 스케줄링은 서로 다른 타임스탬프입니다.

스케줄러는 정책, 우선순위, CPU 적격성에 따라 실행 가능한 작업을 고려합니다. 시간 할당이 만료되면 재고려를 촉발할 수 있지만, 실행 가능한 스레드가 없거나 정책이 달리 말하면 커널은 다른 스레드를 선택하지 않아도 됩니다. 리눅스에는 여러 스케줄링 클래스가 있습니다. "모든 스레드가 정확히 10ms를 받는다"는 일반적 설명이 아닙니다.

## 공유는 중간 상태를 드러낸다

A와 B가 처음에 0인 공유 카운터를 증가시킨다고 합시다. 기계 연산 수준에서 각 증가는 load, 1 더하기, store로 모델링할 수 있습니다. 가능한 인터리빙은 이렇습니다:

```text
A가 0을 로드
B가 0을 로드
A가 1을 계산하고 1을 저장
B가 1을 계산하고 1을 저장
최종 카운터: 1, 두 번의 증가 요청에도
```

이 인터리빙은 잃어버린 갱신을 보여줍니다. C에서 동기화되지 않은 충돌 접근은 일반 공유 변수의 데이터 경합이 되어 정의되지 않은 동작을 일으킬 수 있으므로, 이 표는 컴파일된 모든 결과를 빠짐없이 예측한 것이 아닙니다. 먼저 언어 수준의 원자 연산이나 적절한 동기화로 합법적인 프로그램을 확립하세요.

스케줄러는 여러 명령어에 걸친 증가를 분할 불가라고 약속하지 않았습니다. 하나의 CPU에서도 선점이 연산을 인터리빙할 수 있습니다. 여러 CPU에서는 물리적으로 겹칠 수 있습니다. 타임슬라이스를 줄이거나 연산이 "충분히 빠르다"고 기대하는 것은 동기화 보장을 제공하지 않습니다.

## 반응성은 CPU 속도만의 문제가 아니다

B가 낮은 우선순위 A가 소유한 뮤텍스를 기다리는 고우선순위 소비자라고 상상해 봅시다. 무관한 실행 가능한 작업이 A를 지연시켜 간접적으로 B도 지연시킵니다. 이것이 우선순위 역전이며, 지원되는 우선순위 상속 메커니즘이 필요할 때 소유자가 적절한 유효 우선순위로 실행되게 함으로써 도움을 줄 수 있습니다.

블로킹된 스레드를 모두 데드락이라 부르지 마세요. 완료될 장치를 기다리는 스레드는 평범한 블로킹입니다. 재개될 소유자의 잠금을 기다리는 스레드는 평범한 경합입니다. 진행이 가능한지, 어떤 조건이 그것을 가능하게 하는지, 책임진 생산자가 실행할 수 있는지 조사하세요.

챕터 18은 이 관찰을 동기화 선택으로 바꿉니다: 무엇이 분할 불가여야 하는지, 어떤 컨텍스트에서 잘 수 있는지, 순환 대기를 어떻게 피할지.

## 체크

1. A가 실행하는 동안 장치가 블로킹된 B를 깨웁니다. B의 성공적 웨이크업이 반드시 확립하는 것은?
   - A) B가 즉시 CPU를 소유한다.
   - B) B가 실행 가능해진다.
   - C) B가 이미 결과를 소비했다.
   - Answer: B
   - Explanation: 웨이크업은 스케줄링 상태를 바꿉니다. 실행과 소비는 나중에 일어납니다.

2. 보통 스레드별로 구별되는 것은? 모두 고르세요.
   - A) 실행 레지스터
   - B) 스택 할당
   - C) 프로세스 주소 공간 전체
   - Answer: A, B
   - Explanation: 같은 프로세스의 스레드는 서로의 스택을 포함할 수 있는 주소 공간을 공유합니다.

3. 장치 완료, 웨이크업, 스케줄링, 소비에 타임스탬프를 추가하세요. 장치가 1ms에 완료했는데도 20ms의 애플리케이션 지연이 생기는 구성을 만드세요. 추가 지연을 찾기 위해 어디서 측정해야 하는지 식별하세요.

4. C 카운터를 volatile로 만드는 것이 공유 증가를 고치지 못하는 이유를 설명하세요. 적절한 원자 연산 하나와 락 기반 설계 하나를 제시하고, 각이 보호하는 불변식을 밝히세요.

5. Research challenge: 문서화된 리눅스 스케줄링 정책 하나를 고르세요. 실행 가능한 스레드가 언제 선택될 수 있는지 설명하고, 그 정책에 고정된 보편적 타임슬라이스 설명이 왜 부정확한지 식별하세요.

## 정확성의 경계

상태 표는 stopped, exiting 등 세부 커널 상태를 생략합니다. 스케줄링 동작은 정책과 구성에 따라 달라집니다. 카운터 예시는 기계 수준의 경합을 보여줍니다. 언어 규칙은 정당성 계약의 일부이지 선택적인 세부가 아닙니다.
