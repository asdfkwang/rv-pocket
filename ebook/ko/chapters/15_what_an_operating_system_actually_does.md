# 챕터 15 — 운영체제가 실제로 하는 일

> **Part IV — Protection and the Operating System**

## OS는 하드웨어 메커니즘에 무엇을 더하는가?

권한과 트랩은 통제된 진입을 제공합니다. 그 자체로 프로세스, 파일 디스크립터, 공유 정책을 정의하지는 않습니다. 운영체제는 그 추상화를 유지하고 하드웨어 메커니즘으로 그 규칙을 강제합니다. 프로그램이 유용한 연산을 요청하게 하면서 유한한 CPU 시간, 메모리, 저장장치, 장치를 조율하는 것이 그 일입니다.

챕터 01의 write로 돌아갑니다. 이제 OS라고 적힌 상자를 하나의 명령어나 한 번의 테이블 조회라고 가장하지 않고 풀 수 있습니다. 커널은 요청한 프로세스의 기록과 디스크립터가 선택하는 객체의 표현을 둘 다 필요로 합니다.

## 하나의 디스크립터 번호, 서로 다른 객체

프로세스 A의 디스크립터 3이 직렬 장치에 연결되고 프로세스 B의 디스크립터 3이 일반 파일에 연결됐다고 합시다. 정수 3은 프로세스의 디스크립터 테이블과 함께 있을 때만 의미가 있습니다. 전역 장치 식별자가 아닙니다.

직렬 쓰기에 대해 이 개념적 경로를 씁니다:

```text
A: fd=3, 버퍼에 41, count=1
시스템 콜 진입: 호출자 상태 보존하고 인자 획득
조회: A의 디스크립터 3 -> 열린 직렬 객체
검사: 접근 모드, 버퍼 접근, 객체별 조건
분배: 적절한 파일/서브시스템 연산이 데이터를 받음
직렬 서브시스템/드라이버: 가능하면 큐에 넣고 전송
반환: 결과가 A에게 전달
```

리눅스의 실제 직렬 경로는 하나의 보편적 드라이버 write 콜백 대신 서브시스템 코드를 포함합니다. 중요한 연결은 커널이 선택된 객체의 구현을 통해 추상적 연산을 분배한다는 것입니다. B의 같은 번호 디스크립터는 대신 파일 시스템 경로로 분배됩니다.

버퍼 포인터는 사용자 공간에서 옵니다. 수치 값이 레지스터에 들어가기에 맞다는 이유만으로 신뢰할 수 없습니다. 커널의 사용자 접근 도구가 아키텍처의 접근 검사와 fault 처리를 지원합니다. 커널은 또한 인터페이스에 따라 짧은 전송과 오류를 처리해야 하며, 애플리케이션이 요청한 길이를 사용 가능한 데이터의 증거로 취급해서는 안 됩니다.

## 수락된 작업은 호출보다 오래 살 수 있다

버퍼링된 일반 파일 쓰기를 가정합니다. 커널은 그 파일과 관련된 메모리로 데이터를 복사하고 dirty(백킹 저장소와 다르다)로 표시할 수 있습니다. 나중에 writeback이 저장 작업을 제출합니다. 성공한 쓰기는 파일 인터페이스 아래에서 수락을 기록하며, 전원 실패 후 지속성을 반드시 인증하지는 않습니다.

애플리케이션은 fsync 같은 인터페이스로 더 강한 동기화를 요청할 수 있고 결과를 확인해야 합니다. 파일 내용과 파일을 이름 짓는 디렉터리 항목은 서로 다른 지속성 고려 사항을 가집니다. 챕터 34에서 파일 교체 순서를 다룹니다. flush 연산이 존재한다는 이유로 모든 성공한 쓰기를 "durable"이라 부르면 안 됩니다.

직렬 객체의 경우 관련 완전성은 송신기 drain이나 상대편의 프로토콜 수준 확인일 수 있습니다. "완료"는 관찰하는 경계의 이름을 밝혀야 합니다. 같은 OS 추상화가 구현 세부를 숨기면서도 애플리케이션이 문서화된 보장을 이해하도록 요구할 수 있습니다.

## 격리가 하드웨어의 독립을 뜻하지 않는다

두 프로그램이 메모리는 분리되어 있어도 하나의 장치를 공유할 수 있습니다. OS는 연산을 직렬화하고, 권한을 강제하고, 큐를 제공할 수 있지만 baud rate 구성이 하나뿐인 UART에 두 개의 물리적 baud rate 구성을 만들 수는 없습니다. 일부 충돌에는 더 높은 수준의 공유 정책이나 배타적 소유가 필요합니다.

마찬가지로 파일 잠금은 애플리케이션 메시지 프로토콜을 자동으로 확립하지 않습니다. 애플리케이션이 논리적 갱신의 단위를 정하고 관련 원자성 또는 잠금 인터페이스를 사용해야 합니다. 그렇지 않으면 개별적으로 유효한 두 연산이 둘 다 의도하지 않은 결과로 합쳐질 수 있습니다.

이 예제들은 OS가 서비스 목록 이상의 것임을 보여줍니다. 요청을 가로질러 상태를 유지합니다: 어떤 객체가 열려 있는지, 어떤 데이터가 버퍼링됐는지, 누구가 접근할 수 있는지, 누가 대기 중인지. 챕터 16은 하나의 실행을 멈추고 다른 것을 재개하는 데 필요한 상태에 집중합니다.

## 체크

1. A와 B가 모두 fd = 3으로 write를 호출합니다. 목적지가 달라질 수 있는 이유는?
   - A) 각 디스크립터가 프로세스의 테이블을 통해 해석된다.
   - B) 명령어 인코딩이 목적지를 고른다.
   - C) 디스크립터 3은 항상 UART를 뜻한다.
   - Answer: A
   - Explanation: 핸들의 의미는 커널이 관리하는 프로세스 컨텍스트에 달려 있습니다.

2. 성공한 버퍼링 파일 쓰기에서 따라오는 주장은? 모두 고르세요.
   - A) 결과가 보고한 만큼의 데이터가 수락되었다.
   - B) 갑작스러운 전원 손실 후에도 같은 양이 반드시 지속된다.
   - C) 결과는 여전히 그 객체의 인터페이스에 따라 해석되어야 한다.
   - Answer: A, C
   - Explanation: 수락과 지속성은 서로 다른 보장입니다.

3. 성공한 쓰기와 이후 물리적 완료 사이에 커널이 유지하는 상태를 그리세요. 시스템 콜에서 돌아오는 것이 관련된 모든 커널 작업이 끝났음을 뜻하지 않는 이유를 설명하세요.

4. 두 작성자가 각각 헤더 쓰기 다음 페이로드 쓰기를 합니다. 메시지 형식을 깨는 인터리빙을 제시하세요. 올바른 직렬화 스킴에 필요한 추가 가정을 식별하세요.

5. Research challenge: 리눅스 VFS 문서를 디스크립터에 연결된 파일 객체에서 연산 구현까지 따라가세요. 일반 파일 경로 하나와 문자 장치 경로 하나를 대비하되, 둘 다 같은 드라이버 메서드를 호출한다고 가정하지 말고 서브시스템 경계를 명시하세요.

## 정확성의 경계

시스템 콜 경로는 개념적이며 리눅스의 정확한 검증 순서를 규정하지 않습니다. 권한 정책, 버퍼링, 원자성, 완료 보장은 객체와 연산에 따라 달라집니다. 이 장은 던져야 할 질문을 확립합니다. 뒤의 장들은 특정 인터페이스를 따라갑니다.
