# 챕터 25 — SBI와 리눅스 아래의 경계

> **Part VI — How Linux Finds Hardware**

## 왜 커널은 여전히 펌웨어를 호출하는가?

챕터 24는 평범한 실행을 리눅스에 넘겼지만 기계 수준 제어는 반드시 사라지지 않습니다. SBI(Supervisor Binary Interface)는 supervisor 소프트웨어가 자신의 실행 환경에 요청할 수 있는 서비스를 정의합니다. 흔한 배치는 OpenSBI 같은 M-mode 펌웨어에서 이를 구현합니다. 인터페이스는 다른 구현 환경도 허용합니다.

유용한 경계는 책임입니다: 리눅스는 SBI로 노출된 모든 플랫폼 동작마다 다른 머신 레지스터 순서를 필요로 해서는 안 됩니다. 정의된 서비스를 요청하고 정의된 결과를 받습니다. 이 인터페이스는 평범한 장치 드라이버를 대체하지 않고 모든 하드웨어 동작을 펌웨어 호출로 만들지도 않습니다.

## SBI 호출과 시스템 콜 분리하기

챕터 13은 user 모드 ecall로 OS에 들어갔습니다. SBI ecall은 supervisor 측에서 출발하며 SBI 호출 규약을 씁니다. 현대 SBI 확장에서 a7은 확장 식별자, a6은 함수 식별자, a0–a5는 인자를 담습니다. 반환된 a0은 에러 코드, 정의된 경우 a1은 값을 담습니다. 레거시 확장 규약은 다르며 현대 형태와 조용히 섞어서는 안 됩니다.

사용자 애플리케이션이 자신의 ecall 전에 a7에 SBI 확장 번호를 넣어 supervisor SBI 권한을 얻을 수는 없습니다. 출발 권한과 트랩 라우팅이 요청을 해석할 대상을 결정합니다. 같은 명령어 철자가 서로 다른 소프트웨어 인터페이스에 참여할 수 있습니다.

## 기능을 먼저 조사한 뒤 그 계약을 쓰기

RV64 supervisor가 타이머 서비스를 원한다고 합시다. SBI Base 확장의 probe 함수로 TIME 확장이 가능한지 물을 수 있습니다. 현재 표준 인터페이스의 식별자는 이렇습니다:

```text
확장 probe:
    a7 = 0x10          # Base 확장
    a6 = 3             # probe_extension 함수
    a0 = 0x54494D45    # TIME 확장 식별자
    ecall
    반환된 a0 = 에러; a1 = 가용성 값
```

0이 아닌 가용성 값과 함께 성공한 probe는 그 확장이 사용 가능하다는 뜻입니다. 소프트웨어는 여전히 그 확장의 인자와 에러 규칙을 따라야 합니다. 펌웨어 버전 문자열만으로 무관한 확장의 지원을 추론할 수는 없습니다.

RV64의 TIME set_timer 함수에서 a0은 절대 타이머 값, a6은 0, a7은 TIME을 식별합니다. 현재 시간이 1000틱이고 요청한 마감시각이 1500이라고 합시다. 그 호출은 요청한 타이머 이벤트를 설정합니다. 성공적으로 반환해도 시간이 1500에 도달했거나 supervisor 핸들러가 이미 실행했다는 뜻은 아닙니다.

```text
S-mode: 마감시각 1500 요청
실행 환경: 타이머 기능 준비, 상태 반환
시간이 마감시각까지 진행: 타이머 조건이 대기 상태가 됨
전달 규칙이 서비스 허용: supervisor가 타이머 이벤트 처리
```

이것은 챕터 11의 마감시각, 대기 이벤트, 서비스 시간에 대한 구분을 직접 연결합니다. 관련 아키텍처 타이머 확장이 있는 시스템은 직접 supervisor 타이머 기능을 쓸 수 있습니다. 모든 RISC-V 리눅스 시스템의 모든 타이머 연산이 SBI 호출일 필요는 없습니다.

## 에러는 복구 정책이 아니라 경계를 기술합니다

SBI 함수가 지원하지 않는 연산이나 잘못된 매개변수를 보고하면, 커널은 그 서비스에 따라 결과를 해석해야 합니다. 복구는 다른 지원 메커니즘을 쓰거나, 기능을 비활성화하거나, 실패를 보고하거나, 안전하게 계속할 수 없는 경로를 멈출 수 있습니다. "성공할 때까지 재시도"는 일반적 정책이 아닙니다.

시스템 리셋과 hart 상태 관리는 다른 서비스 범주입니다. 리셋 요청의 성공 동작이 다음 명령어로의 평범한 복귀일 필요는 없습니다. 모든 SBI 호출이 평범한 데이터 반환 함수처럼 동작한다고 가정하지 말고 각 함수의 계약을 읽으세요.

콘솔 진단에도 분리가 필요합니다. 펌웨어 출력, 초기 커널 콘솔, 평범한 UART 드라이버는 서로 다른 경로를 쓸 수 있습니다. 펌웨어 텍스트를 보는 것은 그 시점에 한 경로가 동작했다는 것만 확립합니다. 리눅스가 자체 콘솔을 선택하고 초기화했다는 것을 확립하지 않습니다. 장치 발견이 다음 장의 주제입니다.

## 체크

1. 애플리케이션이 a7에 SBI 확장 ID를 담은 U-mode ecall을 발행합니다. 올바른 해석은?
   - A) 이것만으로 SBI 서비스에 접근할 수 있다.
   - B) 출발 모드와 OS 시스템 콜 경로가 여전히 요청을 지배한다.
   - C) 트랩 라우팅을 우회한다.
   - Answer: B
   - Explanation: 레지스터 값은 권한을 바꾸거나 확립된 트랩 경로 밖의 임의 핸들러를 선택하지 않습니다.

2. 타이머 예제에 대해 옳은 진술은? 모두 고르세요.
   - A) probe 성공은 TIME 가용성을 확립할 수 있습니다.
   - B) 마감시각 1500 설정은 타이머 핸들러가 이미 실행되었음을 증명합니다.
   - C) 마감시각 이벤트와 그 최종 서비스는 별개입니다.
   - Answer: A, C
   - Explanation: 성공한 설정 요청은 미래 이벤트의 완성이 아닙니다.

3. Base probe와 TIME 설정에 걸쳐 레지스터를 추적하세요. 반환된 값을 쓰기 전에 확인해야 하는 결과와 다음 호출에서 다시 불러와야 하는 입력을 식별하세요.

4. 펌웨어 콘솔 출력과 리눅스 초기/평범한 콘솔 출력을 구분하는 부팅 진단을 설계하세요. 동작하는 SBI 구현만으로 평범한 UART 드라이버의 구성이 올바르다는 것을 증명할 수 없는 이유를 설명하세요.

5. Research challenge: 사용 중인 SBI 명세 버전을 살펴보세요. RV32와 RV64의 TIME 인자 레이아웃을 비교하고, 현대 에러/값 쌍에서 추론해서는 안 되는 레거시 호출 규약 하나를 식별하세요.

## 정확성의 경계

이 예제는 RV64에서 표준 현대 SBI 식별자와 흔한 supervisor/펌웨어 배치를 사용합니다. 사용 가능한 확장, 가상화, 직접 아키텍처 기능, 서비스별 비반환 동작은 선택된 환경의 계약을 요구합니다.
