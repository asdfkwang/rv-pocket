# 챕터 32 — 실제 리눅스 드라이버에서의 DMA

> **Part VII — Linux Device Drivers**

## DMA 개념은 리눅스 호출에 어떻게 대응되는가?

챕터 22~23은 세 가지 의무를 확립했습니다: 장치에 보이는 주소를 쓸 것, 소유권을 올바르게 전이할 것, 필요한 가시성/순서를 확립할 것. 리눅스 DMA API는 드라이버가 특정 캐시나 IOMMU 구현을 하드코딩하지 않고도 이 의무를 표현합니다.

16바이트 송신 버퍼를 읽는 장치를 사용합니다. 설정 중 드라이버는 실제 하드웨어와 플랫폼이 지원하는 DMA 마스크를 선택하고, 결과를 검사하고, 지원하지 않는 구성을 거부합니다. 32비트 주소 레지스터는 검사하지 않은 잘린 64비트 DMA 주소를 안전하게 받을 수 없습니다.

## 성공하는 스트리밍 매핑 추적하기

다음 조각은 kmalloc 기반 송신 버퍼와 정상적인 성공 생명주기를 설명합니다. 장치 특적 채움, 제출, 완료 프로토콜은 드라이버가 제공해야 합니다.

```c
void *buf = kmalloc(16, GFP_KERNEL);
if (!buf)
    return -ENOMEM;
fill_payload(buf, 16);

dma_addr_t addr = dma_map_single(dev, buf, 16, DMA_TO_DEVICE);
if (dma_mapping_error(dev, addr)) {
    kfree(buf);
    return -EIO;
}
/* addr와 길이 16을 제출; 장치가 소유하는 동안 페이로드는 건드리지 않음 */
```

CPU는 할당/수명 관리를 위해 buf를 유지합니다. 하드웨어는 자신의 DMA 주소 공간에서 해석되는 `dma_addr_t` 값인 addr를 받습니다. 하드웨어에 buf를 주지 말고, 페이로드를 살펴보기 위해 addr를 CPU 포인터로 캐스팅하지도 마세요.

장치 프로토콜이 이 전송의 버퍼에 대한 모든 접근이 끝났음을 증명한 뒤:

```c
dma_unmap_single(dev, addr, 16, DMA_TO_DEVICE);
kfree(buf);
```

장치, 크기, 방향, 매핑 종류는 매핑 연산과 대응해야 합니다. 하드웨어가 버퍼에 접근할 수 없기 전에 제출이 실패했다면 매핑과 할당을 되돌리세요. 제출이 하드웨어에 도달했을 수 있다면, 취소는 그 되돌리기 전에 정지 상태를 확립해야 합니다. unmap 호출 자체는 엔진을 멈추지 않습니다.

## 수신과 재사용은 명시적 전이가 필요하다

수신 버퍼에서는 장치가 메모리에 쓰므로 DMA_FROM_DEVICE를 사용하세요. 완료를 확정한 뒤 일치하는 unmap 연산으로 매핑을 끝내면 그 생명주기 아래에서 CPU가 수신된 내용을 소비할 수 있습니다. 매핑을 반복 전송에 걸쳐 유지한다면 소유권 전이 지점에서 적절한 sync-for-CPU와 sync-for-device 연산을 사용하세요.

재사용 가능한 매핑은 일부 설정 작업을 아끼지만 상태 관리를 더 명시적으로 만듭니다. 포인터가 여전히 존재한다는 이유만으로 CPU가 장치 소유 버퍼를 살펴보면 안 됩니다. 오래된 페이로드는 누락된 동기화에서 생길 수 있고, 손상된 페이로드는 겹치는 소유권, 잘못된 길이, 장치가 다른 곳에 쓰는 것에서도 생길 수 있습니다. 어떤 보장이 실패했는지 진단하세요.

사용자 버퍼에는 서브시스템별 고정(pinning)과 매핑 규칙이 적용됩니다. 사용자 공간 가상 포인터는 `dma_map_single`에 적합한 인자가 아닙니다. 고정은 그 API 아래 페이지 수명을 확립하지만 그 자체로 임의 범위에 하나의 연속 장치 주소를 만들지는 않습니다. 전체 설계는 scatter/gather 배치, 접근 권한, unpinning, 취소를 다루어야 합니다.

## 일관적인 디스크립터와 scatter/gather 페이로드

`dma_alloc_coherent`는 CPU 접근 가능 포인터와 적절한 공유 제어 메모리를 위한 별도의 DMA 핸들을 반환합니다. 일관적인 가시성에 대한 스트리밍 소유권 동기화를 피하지만 디스크립터 순서 배어나 수명 의무를 없애지는 않습니다. 하드웨어가 더 이상 접근하지 않은 뒤 대응하는 일관적 해제 연산과 짝지으세요.

여러 적절한 세그먼트에 걸친 페이로드에는 `dma_map_sg`가 scatterlist를 매핑합니다. 매핑이 세그먼트를 합칠 수 있기 때문에 반환된 매핑 세그먼트 수는 원래 항목 수보다 작을 수 있습니다. 매핑된 DMA 세그먼트를 사용해 하드웨어를 설정하되, 문서대로 대응하는 unmap/sync API에는 원래 입력 개수를 전달하세요. 그 개수들을 혼동하면 아키텍처 의존 버그가 생깁니다.

## 타임아웃과 제거를 일급 경로로 만들기

타임아웃 시 새 제출을 멈추고, 프로토콜에 따라 관련 엔진을 멈추거나 리셋하고, 완료 경로를 동기화하고, 장치 접근이 불가능해진 뒤에만 매핑을 회수하세요. 제거는 모든 진행 중 버퍼에 같은 요구를 추가합니다. 자동 자원 정리는 안전한 DMA 정지 순서를 추론할 수 없습니다.

챕터 33은 사용자 공간 계약으로 나아갑니다. 올바른 DMA 이동은 애플리케이션의 read나 write 결과가 약속하는 것의 한 부분일 뿐입니다.

## 체크

1. 장치의 DMA 주소 필드에 어떤 값을 설정해야 합니까?
   - A) CPU의 buf 포인터
   - B) 그 장치와 매핑에 대해 검증된 DMA 핸들
   - C) 포인터를 캐스팅해 추론한 임의의 물리 주소
   - Answer: B
   - Explanation: 매핑 API는 장치의 주소 관점과 플랫폼 제약을 반영합니다.

2. 어떤 것이 유효한 생명주기 의무입니까? 모두 고르세요.
   - A) 매핑 실패를 검사한다.
   - B) unmap의 크기와 방향을 매핑과 맞춘다.
   - C) 타임아웃을 DMA가 멈췄다는 증거로 취급한다.
   - Answer: A, B
   - Explanation: 타임아웃은 소프트웨어 대기를 끝낼 뿐입니다. 안전한 회수에는 완료 또는 정지 상태가 필요합니다.

3. 세 번 사용한 지속적 수신 매핑의 완전한 소유권 상태 머신을 그리세요. 각 결과를 읽을 수 있는 지점과 최종 unmap/free를 포함하세요.

4. `dma_map_sg`가 여섯 항목을 받고 네 개 DMA 세그먼트를 반환합니다. 어떤 개수가 장치 설정을 구동하고 어떤 개수가 unmap에 쓰입니까. 개수들을 바꿔 쓰면 어떤 실패가 생깁니까.

5. Research challenge: 기록된 리비전에서 업스트림 드라이버의 매핑 실패와 타임아웃 경로를 살펴보세요. 늦은 IRQ나 workqueue 경로를 포함해, 해제 전에 버퍼에 장치가 더 이상 접근할 수 없음을 어떻게 증명하는지 식별하세요.

## 정확성의 경계

코드 조각은 성공하는 매핑 모양 하나를 보일 뿐 완전한 DMA 드라이버는 아닙니다. 하드웨어 마스크, 디스크립터 형식, 할당 제한, 경계 한계, DMA 방향은 실제 장치와 일치해야 합니다. 커널 DMA 도구는 하드웨어의 완료 및 리셋 프로토콜을 대체하지 않습니다.
