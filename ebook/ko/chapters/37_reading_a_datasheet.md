# 챕터 37 — 데이터시트 읽기

> **Part VIII — A Complete System**

## 데이터시트를 어떻게 실행 가능한 프로토콜로 바꾸는가?

앞의 장들은 작은 장치 계약을 명시적으로 제공했습니다. 실제 드라이버 작성자는 그 계약들을 레지스터 표, 타이밍 다이어그램, 리셋 순서, 통합 노트, 에라타에서 추출해야 합니다. 레지스터 이름만 읽으면 가장 중요한 순서와 수명 규칙을 발견하지 못합니다.

"메모리에 256바이트를 캡처한다"처럼 수행하고 싶은 연산에서 시작하세요. 그 연산의 사전 조건, 명령 순서, 완료 증거, 복구 절차를 수집합니다. 모호한 단위나 접근 타입은 코드를 쓰기 전에 해결해야 할 질문입니다.

## 작은 명세에서 연습하기

다음은 이 장을 위해 UART와 분리해 발명한 캡처 엔진 발췌입니다. 레지스터는 정렬된 32비트 리틀 엔디안 MMIO입니다. 접근 전에 클록이 활성화되고 리셋이 해제되어야 합니다. 수신 데이터를 DMA 버퍼에 씁니다.

| 오프셋 | 레지스터 | 접근과 의미 |
| --- | --- | --- |
| `0x00` | ADDRESS | RW, 32비트 DMA 주소, 16바이트 정렬 필수 |
| `0x04` | LENGTH | RW, 바이트 수, 0이 아닌 4의 배수, 최대 4096 |
| `0x08` | COMMAND | 쓰기 전용, 유휴 상태일 때 비트 0이 시작 |
| `0x0C` | STATUS | RO, 비트 0 바쁨; 리셋 완료 후 0 |
| `0x10` | EVENTS | W1C, 비트 0 완료, 비트 1 오류 |
| `0x14` | ID | RO, 기대값 `0x52565031` |

추가 규칙: ADDRESS와 LENGTH는 바쁜 동안 바뀌면 안 됩니다. START는 이전 이벤트 비트를 지우지 않습니다. DONE은 그 전송에 대한 모든 쓰기가 완료되고 장치가 더 이상 그 버퍼에 접근하지 않을 때만 주장됩니다. 오류나 타임아웃 시, 매핑을 회수하기 전에 문서화된 abort/reset 절차가 필요합니다. 리셋은 지정된 동작 조건에서 최대 100개의 활성화된 장치 클록 주기를 요구합니다.

이 문장들은 표만큼이나 많은 드라이버 로직을 담고 있습니다. 특히, 이전 DONE 비트는 소프트웨어가 제때 지우지 않으면 새로운 완료로 오해될 수 있습니다.

## 유효한 256바이트 캡처 유도하기

32비트 DMA 마스크가 지원되고, 256바이트 수신 버퍼의 매핑이 `0x40002000`을 반환하며, 설정이 안정적인 50MHz 장치 클록을 활성화했다고 가정합니다. 주소는 16바이트 정렬을 만족하고 길이는 합법적인 4의 배수입니다.

드라이버는 유휴 상태를 확립하고, 문서화된 W1C 마스크로 오래된 이벤트 비트를 확인하고, ADDRESS와 LENGTH를 설정하고, 필요한 I/O 순서와 함께 START를 제출합니다. 그 뒤 DONE 또는 처리된 실패가 나올 때까지 버퍼를 장치 소유로 둡니다. DONE 이후 바이트를 검사하기 전에 DMA API의 CPU 접근 전이를 수행합니다.

```text
주소 검사: 0x40002000 & 0xF = 0
길이 검사: 256 % 4 = 0, 그리고 0 < 256 <= 4096
길이 레지스터 값: 0x100, 바이트 기준
50MHz에서 리셋 최대: 100 / 50,000,000 s = 2 마이크로초
```

리셋 타이밍 계산은 필요한 클록이 실제로 돌고 있다는 것을 가정합니다. 2마이크로초의 CPU 지연은 클록 게이트된 장치에서 진행이 일어나게 할 수 없습니다. 소프트웨어 타임아웃 정책도 관찰 지연과 문서화된 타이밍 여유를 고려해야 합니다. 계산된 하드웨어 구간이 보편적 폴링 루프 지속 시간은 아닙니다.

## 그럴듯한 잘못된 구현 검토하기

드라이버가 256을 4바이트 버스 너비로 나누므로 LENGTH = 64를 씁니다. 하지만 그 레지스터는 바이트를 세므로 엔진은 64바이트만 캡처합니다. 두 번째 버그는 이전 DONE을 지우려고 EVENTS에 0을 씁니다. W1C 의미는 그 비트를 설정된 채 남깁니다. 다음 대기는 새 캡처가 끝나기 전에 완료를 보고합니다.

두 버그 모두 올바른 기준 주소, 올바른 readl/writel 너비, 성공한 probe와 함께 발생할 수 있습니다. 단위와 접근 의미가 틀렸던 것입니다. 오래된 완료 경합을 감추는 임의의 더 긴 지연을 추가하는 대신 프로토콜을 고치세요.

ID는 선택한 영역이 기대 장치와 비슷한지 테스트하는 데 도움이 될 수 있지만, 한 번의 올바른 ID 읽기가 클록 안정성, 인터럽트 배선, DMA 접근 가능성, 실리콘 리비전별 동작을 인증하지는 않습니다. 증거에는 범위가 있습니다.

## 계약 장부 유지하기

각 연산에 대해 명세가 주소와 단위, 합법적 접근 너비, 예약 비트 처리, 사전 조건, 완료, 동시 접근, 복구를 어디서 정의하는지 기록하세요. 리비전/에라타 참조를 붙이세요. 진술이 없으면 예제 프로그램에서 보장을 만들어 내지 말고 미해결로 표시하세요.

챕터 38은 같은 장부를 역방향으로 적용합니다: 기존 드라이버 코드를 읽고 그것이 구현하려고 하는 프로토콜을 복원합니다.

## 체크

1. 이 엔진에서 256바이트를 요청하는 LENGTH 값은?
   - A) 64
   - B) `0x100`
   - C) `0x1000`
   - Answer: B
   - Explanation: LENGTH는 MMIO 버스 접근 너비와 독립적으로 바이트를 셉니다.

2. 발췌에 어긋나는 요청은? 모두 고르세요.
   - A) ADDRESS = `0x40002008`
   - B) LENGTH = 258
   - C) STATUS.busy가 설정된 동안 LENGTH 갱신
   - Answer: A, B, C
   - Explanation: 이들은 각각 정렬, 개수 세분성, 활성 전송 갱신 규칙을 위반합니다.

3. 이전 DONE 이벤트가 설정된 채 남겨서 발생하는 거짓 성공 타임라인을 보이세요. 올바른 W1C 확인이 임의의 나중 시점이 아니라 제출 프로토콜과 결합되어야 하는 이유를 설명하세요.

4. 클럭이 50MHz가 아니라 25MHz입니다. 리셋 최대 구간을 다시 계산하고, 클록 활성화나 리셋 배선이 잘못되었다면 그 결과조차 리셋 완료를 증명할 수 없는 이유를 설명하세요.

5. Research challenge: 실제 데이터시트를 하나 고르고 한 연산에 대한 계약 장부를 재현하세요. 에라타 하나를 포함하거나 에라타를 확인했다는 사실을 명시하세요. 문서가 보장하는 것과 샘플 드라이버가 가정하는 것을 구분하세요.
