# 챕터 13 — 예외, 트랩, 시스템 콜

> **Part III — CPU Meets Hardware**

## 왜 실행이 명령어 스트림을 벗어났는가?

챕터 12는 하드웨어 알림을 따라갔습니다. RISC-V는 인터럽트나 예외로 인한 제어 전이를 더 넓은 용어인 트랩으로 부릅니다. 인터럽트는 인터럽트된 명령어 스트림에 대해 비동기적입니다. 예외는 illegal instruction, 실패한 메모리 접근, 환경 호출처럼 특정 명령어 실행과 연관됩니다.

시스템 콜은 커널 서비스를 요청하기 위해 의도적인 예외를 씁니다. `ecall` 명령어 자체가 "바이트 하나를 써라"를 뜻하지는 않습니다. 그 의미는 현재 권한 레벨과 호출하는 소프트웨어 규약에 달려 있습니다. 트랩 핸들러가 요청을 해석하고 다음에 무엇을 할지 결정합니다.

## 진입 기록은 시작점이다

supervisor 모드 OS와 user 모드 프로그램을 가정하고 관련 user 트랩이 supervisor로 위임되었다고 합시다. 그 권한 레벨과 위임은 챕터 14에서 설명합니다. 직접 트랩 벡터 모드에서 진입은 stvec에 설정된 기준 주소를 씁니다. 하드웨어는 sepc를 반환/명령어 주소로, scause를 사유로, 관련 상태 필드를 갱신합니다. stval은 예외 규칙에 따라 fault 주소 같은 추가 정보를 담을 수 있습니다.

이 CSR(제어 및 상태 레지스터)은 산술에 쓰이는 범용 레지스터가 아닙니다. 진입 어셈블리도 범용 레지스터를 보존하고 적절한 스택을 세운 뒤 평범한 커널 코드를 실행해야 합니다.

`0x4000`의 user 프로그램이 리눅스 서비스를 요청한다고 합시다. 래퍼는 시스템 콜 번호를 a7에 인자를 a0부터 넣고 ecall을 실행합니다. user 환경 호출 예외에 대해 동기 예외 코드는 8입니다. 이 예제에서 위임은 기계 모드 펌웨어가 아니라 supervisor로 라우팅합니다.

```text
진입 전: user PC=4000; a7=요청 번호; a0...=인자
하드웨어:  sepc=4000; scause=8; supervisor 트랩 벡터로 진입
소프트웨어: 레지스터 저장; 요청 검증; 서비스 실행
소프트웨어: 저장된 a0=결과; 완료된 이 ecall에 대해 sepc=4004
종료:    레지스터 복원; sret이 4004에서 user 코드를 재개
```

ecall 명령어는 4바이트이므로 저장된 이 PC를 4만큼 증가시키면 완료된 요청을 건너뜁니다. 이것은 핸들러의 결정입니다. 범용 트랩 핸들러는 원인과 무관하게 모든 저장된 PC를 4씩 증가시켜서는 안 됩니다.

## 재시도는 건너뛰기와 다르다

`0x5000`의 load가 프로세스 주소 공간의 유효한 일부를 참조하지만 그 페이지가 현재 설치되지 않았다고 합시다. OS가 페이지를 제공할 수 있다면 매핑을 고치고 sepc가 여전히 `0x5000`인 채로 반환합니다. load가 다시 실행되어 이번에는 완료될 수 있습니다. `0x5004`로 진행하면 load를 건너뛰어 목적지에 의도한 결과가 없는 상태로 남습니다.

접근이 정책을 위반하면 OS는 대신 프로세스에 신호를 보내거나 종료할 수 있습니다. 커널 fault도 컨텍스트에 따라 다릅니다: 권한이 있는 사용자 메모리 복사 중 발생한 fault에는 정의된 복구 경로가 있을 수 있지만, 예기치 않은 커널 포인터 fault는 심각한 버그를 나타낼 수 있습니다. "커널 fault"가 자동으로 하나의 보편적 결과를 뜻하지는 않습니다.

비동기 인터럽트의 경우 저장된 PC는 인터럽트된 계산이 재개될 위치를 나타냅니다. 장치가 주목을 필요로 했다는 이유만으로 어떤 명령어도 건너뛰지 않습니다. 따라서 하나의 진입 메커니즘이 서로 다른 세 가지 반환 정책을 지원합니다: 완료된 요청 뒤 계속, 고쳐진 faulting 명령어 재시도, 비동기 서비스 뒤 재개.

## 명세가 원인을 식별하게 하라

직관적인 고수준 오류가 항상 하드웨어 예외인 것은 아닙니다. 관련 RISC-V 정수 나눗셈 지원이 있으면 0으로 나누는 것은 정의된 몫/나머지 결과를 만들며 0 나눗셈 trap을 올리지 않습니다. 지원하지 않는 명령어 인코딩은 별개의 문제로 illegal-instruction 예외를 만들 수 있습니다.

디버깅은 기록된 원인, 저장된 PC, 명령어 바이트, 관련 주소 정보로 시작합니다. "trap"만 출력하는 핸들러는 나쁜 포인터, 지원하지 않는 명령어, 의도적인 시스템 콜을 구분하는 데 필요한 증거를 버립니다.

다음 장은 핸들러가 요청한 애플리케이션이 갖고 있지 않은 권한을 왜 갖고 있는지, 그리고 어떤 상태가 사용자 프로그램이 그 권한을 스스로 부여하는 것을 막는지를 설명합니다.

## 체크

1. OS가 `0x5000`의 load에서 발생한 복구 가능한 페이지 fault를 고쳤습니다. 그 연산을 보통 어디서 재개해야 합니까?
   - A) `0x5000`
   - B) 항상 `0x5004`
   - C) 적재된 데이터의 주소
   - Answer: A
   - Explanation: load를 재시도하면 값을 얻습니다. 건너뛰면 계산이 불완전해집니다.

2. 옳은 사실은? 모두 고르세요.
   - A) ecall은 어떤 레지스터 규약 없이도 리눅스 서비스를 식별합니다.
   - B) scause는 기록된 트랩 사유를 구분합니다.
   - C) 소프트웨어는 인터럽트된 계산에 필요한 범용 레지스터를 보존해야 합니다.
   - Answer: B, C
   - Explanation: 소프트웨어 규약이 ecall 인자에 의미를 부여합니다. 트랩 메타데이터는 완전한 레지스터 저장이 아닙니다.

3. user ecall, 복구 가능한 load 페이지 fault, 외부 인터럽트를 비교하는 표를 만드세요. 출처, 저장된 PC의 의미, 핸들러 동작, 반환 PC 정책을 포함하세요.

4. 핸들러가 sepc에 무조건 4를 더합니다. 재시도와 관련된 시나리오 하나, 명령어 길이나 비동기 인터럽트와 관련된 다른 시나리오 하나를 만들어 실패를 보이세요. 핸들러의 규칙에서 빠진 정보가 무엇인지 설명하세요.

5. Research challenge: 권한 없는 ISA의 정수 0 나눗셈 동작과 권한 ISA의 user ecall 예외 코드를 확인하세요. 트랩 증거만으로 지원되는 divide 명령어에 0 피연산자를 준 경우와 지원되지 않는 divide 명령어를 어떻게 구분합니까?

## 정확성의 경계

이 예제는 S-mode 직접 벡터 진입과 명시적 위임을 선택합니다. 다른 구성은 M-mode로 진입하거나 벡터형 인터럽트 진입을 씁니다. 시스템 콜 레지스터 규약은 OS ABI이며, 완전한 리눅스 진입 코드는 이 개념적 추적보다 많은 상태를 처리합니다.
