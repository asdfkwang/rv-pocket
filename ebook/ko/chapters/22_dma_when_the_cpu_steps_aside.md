# 챕터 22 — DMA: CPU가 비켜설 때

> **Part V — Memory Becomes Virtual**

## 장치가 스스로 메모리에 접근하면 무엇이 바뀌는가?

지금까지는 CPU가 RAM과 장치 레지스터 사이에서 데이터를 옮겼습니다. DMA(Direct Memory Access)는 CPU가 매 바이트마다 load/store 루프를 실행하지 않고도 장치나 DMA 엔진이 데이터를 전송하게 합니다. CPU는 여전히 작업을 설정하고, 접근 가능한 버퍼를 준비하고, 완료를 처리하고, 오류를 관리합니다.

DMA는 자체 주소 해석과 타이밍을 가진 또 다른 메모리 행위자를 도입합니다. 따라서 핵심 문제는 소유권입니다: 언제 CPU가 버퍼를 바꿀 수 있는가, 언제 장치가 그것을 읽거나 쓸 수 있는가, 어떤 이벤트가 그것을 CPU 사용으로 돌려주는가?

## 송신 버퍼 하나 추적하기

장치가 메모리에서 16바이트 패킷을 읽어 외위로 보낸다고 가정합니다. CPU는 버퍼로 가리키는 커널 포인터 K를 갖고 있습니다. DMA 매핑 인터페이스를 통해 장치 주소 D = `0x40002000`를 얻습니다. 그 매핑은 IOMMU(장치 요청용 하드웨어 변환 유닛)나 다른 플랫폼 메커니즘을 포함할 수 있습니다. D는 CPU의 물리 주소와 같을 필요가 없으며 CPU가 역참조해서는 안 되는 포인터입니다.

```text
CPU 소유: 버퍼 할당; 페이로드 16바이트 채움
준비:    DMA 매핑과 장치 읽기에 필요한 가시성 확보
공개:    장치 주소 D와 길이 16 제출; 연산 시작
장치 소유: 장치가 버퍼를 읽는 동안 CPU는 페이로드를 건드리지 않음
완료:    장치 특화 증거가 버퍼 접근이 끝났음을 증명
회수:    필요에 따라 동기화/unmap; CPU가 버퍼를 재사용하거나 해제 가능
```

장치가 패킷을 읽는 동안 CPU가 바이트 8을 바꾸면 전송 결과에 오래된 접두사와 새로운 접미사가 섞일 수 있습니다. 빠른 CPU나 일관적인 인터커넥트도 빠진 소유권 협의를 고쳐주지 않습니다. 장치는 자신의 연산 중에 내용이 바뀐 버퍼를 관찰했습니다.

마찬가지로 DMA를 시작하는 레지스터 쓰기는 완료가 아닙니다. 그 직후 unmap하거나 해제하면 장치의 접근이 제거되거나 지금 다른 것에 배정된 메모리를 읽게 될 수 있습니다. 버퍼는 제출이 권한 부여한 모든 장치 접근보다 오래 살아야 합니다.

## 디스크립터는 작업을 기술할 뿐 작업이 아니다

많은 장치는 주소, 길이, 제어 플래그를 담은 디스크립터를 읽습니다. 링은 큐잉된 연산을 위해 그런 디스크립터 여러 개를 구성합니다. CPU는 디스크립터를 준비한 뒤 플래그, 인덱스, 또는 MMIO 도어벨(작업이 준비됐음을 하드웨어에 알리는 레지스터 쓰기)을 통해 소유권을 장치에 공개합니다.

디스크립터 0에 D = `0x40002000`, 길이 16, 소유권 비트가 처음에는 0이라고 가정합니다. CPU는 장치의 순서 규약 아래에서 소유권을 설정하기 전에 주소와 길이가 보이도록 해야 합니다. 그렇지 않으면 장치는 오래된 길이나 주소를 가진 채 "준비됨"을 볼 수 있습니다. 챕터 23에서 이 순서 요구를 캐시 가시성과 분리합니다.

페이로드 버퍼와 디스크립터는 수명과 접근 패턴이 다릅니다. 장치는 디스크립터를 한 번 읽지만 그 이후에도 페이로드를 계속 읽을 수 있습니다. 따라서 디스크립터 페치를 관찰하는 것으로 페이로드를 해제할 수 있다고 증명하지는 않습니다. 완료와 프리페치 또는 반복 접근 동작은 장치 명세가 식별해야 합니다.

## 수신은 데이터 방향을 뒤집는다

수신 DMA에서는 장치가 버퍼에 바이트를 씁니다. CPU는 완료를 기다리고 데이터를 읽기 전에 CPU 접근으로 필요한 전이를 수행해야 합니다. 리눅스 DMA API의 방향 이름은 장치 관계 기준입니다: DMA_TO_DEVICE는 장치가 메모리를 읽는다는 뜻이고 DMA_FROM_DEVICE는 장치가 메모리에 쓴다는 뜻입니다.

비일관적 시스템에서는 소유권 전이 시점에 캐시 유지보수가 필요할 수 있습니다. IOMMU 매핑은 장치가 주소할 수 있는 메모리에 답하고, 캐시 동기화는 어떤 내용이 보이는지에 답합니다. 하나가 다른 것을 자동으로 대체하지는 않습니다.

타임아웃 복구도 소유권 문제입니다. 타임아웃은 소프트웨어가 대기를 멈췄다는 것을 증명할 뿐 장치가 메모리 접근을 멈췄다는 것이 아닙니다. 복구는 엔진을 멈추거나 리셋하고 정지 상태를 확립한 뒤 버퍼를 해제해야 합니다. 이 추론이 챕터 32에서 실제 리눅스 생명주기를 이끕니다.

## 체크

1. 장치가 제출된 송신 버퍼를 읽기 시작했습니다. CPU는 언제 해제할 수 있습니까?
   - A) 시작 레지스터에 쓴 직후
   - B) 프로토콜이 장치 접근 종료를 증명하고 필요한 회수 연산이 완료된 후
   - C) CPU가 원래 포인터 값을 더 이상 필요로 하지 않을 때
   - Answer: B
   - Explanation: 버퍼가 안전하게 해제되는 시점은 CPU 명령어 완전이 아니라 장치 수명이 결정합니다.

2. 옳은 진술은? 모두 고르세요.
   - A) DMA 주소는 항상 평범한 커널 포인터입니다.
   - B) 매핑과 페이로드 가시성은 별개의 관심사입니다.
   - C) 타임아웃만으로 장치가 유휴하다고 증명할 수 없습니다.
   - Answer: B, C
   - Explanation: 장치 주소 지정, 가시성, 완료는 서로 다른 계약입니다.

3. CPU가 버퍼를 너무 일찍 재사용해 장치가 새/오래된 패킷이 섞인 패킷을 전송하는 타임라인을 구성하세요. 메모리 배리어만으로 어떻게 CPU에 소유권을 돌려줄 수 없는지 설명하세요.

4. 이름 붙은 상태와 합법적 전이를 갖는 수신 버퍼 생명주기를 설계하세요. 메모리를 해제하기 전에 정상 완료, 매핑 실패, 타임아웃 복구를 포함하세요.

5. Research challenge: 리눅스 DMA 가이드를 참고해 어떤 메모리 할당이 `dma_map_single`에 적합한지 확인하세요. 임의의 사용자 공간 포인터나 가상적으로 연속인 할당을 예제에 그대로 대입할 수 없는 이유를 설명하세요.

## 정확성의 경계

이 장은 일반적인 DMA capable 주변장치를 기술하며 고정된 디스크립터 형식이나 인터럽트 프로토콜 하나를 다루지 않습니다. 하드웨어는 메모리를 프리페치하거나 큐에 넣거나 반복 접근할 수 있습니다. 리눅스 DMA API는 문서화된 소유권 계약에 따라 쓰일 때 플랫폼 매핑과 동기화 세부사항을 처리합니다.
